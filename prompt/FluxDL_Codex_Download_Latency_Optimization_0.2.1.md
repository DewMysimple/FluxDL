# FluxDL 0.2.1 — Download Latency Optimization

> **给 Codex 的完整工程执行任务书**  
> **主题**：Faster Start, Clearer Progress（更快开始下载、更清楚地解释等待）  
> **目标工程**：`https://github.com/DewMysimple/FluxDL`  
> **目标平台**：Windows 10/11 x64；React + TypeScript + Vite / Tauri 2 + Rust / yt-dlp  
> **目标性质**：基于真实诊断数据进行下载启动性能优化，保持现有功能、数据安全和 Midnight Glass UI 一致。  
> **执行方式**：直接在现有仓库审计、实施、测试、记录并按项目现有协作规则交付；**不要只输出计划或概念代码**。

## 0. 给 Codex 的最高优先级指令

你是负责 FluxDL 的资深桌面客户端、Rust 异步任务、yt-dlp 集成、性能诊断和测试工程师。当前已有第一版产品、0.2.0 工程重构、正式构建流水线，以及诊断中心（概览、性能、事件、异常）。

本轮**不重写应用，不增加播放列表 / 并发下载等大功能**，重点解决实际用户体验中「解析视频、加入下载队列，再到真正看到下载进度，等待时间较长」的问题。

你必须完成以下闭环：

1. **读真实仓库和诊断证据** → 确认实际代码路径与现有测试。
2. **建立可重复的旧实现基线** → 区分本地固定测试与外部站点波动。
3. **细分下载启动后的未知时间** → 精确找到子进程已启动但进度尚未出现期间的可观察节点。
4. **实施后端可信解析结果复用** → 尝试消除冗余二次元数据网络提取；安全复核不能被跳过。
5. **改善用户看到的真实等待状态** → 不伪造状态、预计剩余时间或进度。
6. **贯通任务详情与诊断** → 能直接从某个任务查看它的相关 Trace。
7. **完成 A/B 测试、性能复测与回归** → 输出原始样本、统计结果及任何失败、回退。
8. **按已有仓库协作规范交付** → 尊重 `AGENTS.md`、`wiki_memory/`、Git/发布流程。

**技术目标不等于保证某个网站一定快多少秒。** 只有来自相同测试条件的真实数据，才允许用于宣称性能改善；外部网络、站点和 yt-dlp 自身耗时必须如实说明。

## 3. 阶段 0：仓库审计、现状记录与基线复现

### 3.1 先查真实数据流

定位并画清：

```text
用户点击解析 → 前端 IPC → Rust 解析命令 → yt-dlp 元数据 → 预览 DTO
    → 用户停留 / 选择格式（不计入软件处理耗时）
    → 点击入队 → Rust 基本校验 → 再次 yt-dlp 复核
    → 任务持久化 → 串行调度 → yt-dlp download spawn
    → engine 活动 / before_dl（如可观察）→ 首个有效进度
    → 下载 → 后处理 → 文件核验 → 最终落库
```

检查实际命令行参数、进程 stdout/stderr 管线、进度解析器、当前 typed events、trace 关联、attempt 终态，以及何处真正发生第二次网络提取。

特别检查：

- 是否下载子进程本身还要重新提取站点元数据；这是正常 yt-dlp 行为还是当前代码重复做了更多工作。
- 是 spawn 很快，但后续没有可观察事件，还是输出被缓冲、解析器没识别、媒体无 progress hook。
- 如果音视频分开下载，哪些格式只有进入片段下载后才会触发 progress。
- yt-dlp 需要 JS / EJS、FFmpeg、网络访问、DNS/TLS、站点认证等外部依赖，但**不将它们未经测量地标为根因**。
- UI 现在如何表达 `Queued / Preparing / Downloading / PostProcessing`，是否误导用户。

### 3.2 找本机诊断数据

开发版若存在 `dev-logs/latest-report.md` 及 `dev-logs/sessions/*.jsonl`，先读取并选出当前所用源码对应的真实会话。

若只有本任务书所列单次样本、或本机诊断目录不存在：

- 执行可控本地 fixture 测试，生成真正可重复的基线。

## 4. 阶段 1：下载引擎的细粒度启动耗时追踪（P0）

### 4.1 核心要求

在现有诊断框架上最小范围扩展，不创建第二套日志系统、独立数据库或重复 Trace 协议。

目标是解释旧阶段 `download_engine_spawn → download_first_progress` 期间的 32.95 秒到底有多少可被进一步分段观察，**而不是声称能精确知道 DNS/TLS/站点内部时间**。

### 4.2 建议的时间节点

根据 yt-dlp 当前版本实际能力选择适用节点，以下为期望语义：

| 建议语义 | 真正可测边界 | 明确不代表 |
|---|---|---|
| `download_process_spawn` | Rust 发出 spawn 前 / 返回子进程句柄后 | 引擎已连接站点 |
| `download_first_output` | stdout/stderr 任一管线第一次读到数据的单调时间（只记时间/管线类型） | 网络请求开始、已下载首字节 |
| `download_before_dl` | yt-dlp 被验证能输出的下载前阶段安全标记（如果支持） | 已经收到媒体字节 |
| `download_first_protocol_progress` | 首个成功解析且通过 task/attempt 准入的进度消息 | 网络首字节、下载总时长 |
| `download_postprocess_start` | 当前真正的后处理信号 | 下载已经完整成功 |
| `download_process_exit` | 子进程实际退出且输出处理完成 | 最终业务落盘已确认 |

**命名依照当前 Rust `Phase` 枚举和项目规范确定。** 不重复创建已有阶段，也不随意修改现有字段含义；需要更新 Schema 时提供向后兼容或显式版本迁移与测试。

### 4.3 如何实施安全标记

- 优先使用现有 stdout/stderr reader 中的**固定、安全、可识别的非媒体数据标记**。
- 可以研究 yt-dlp 的 `--print before_dl:<固定标记>`（具体语法、触发时机以现有 yt-dlp 版本为准）；先做独立 fixture 验证，确保不会隐式进入模拟模式、抑制进度、改变下载格式、破坏 JSON 管线或改变进程退出码。
- 如 `--print` 会影响现有行为，**宁可放弃该标记**，保留已证实的节点，不得硬改下载逻辑。
- 不直接记录标题、URL、命令行参数、媒体路径、原始 stdout/stderr、Cookie、Token、认证 Header 或代理凭据。
- 如果需要识别输出，采用明确命名空间的固定标记，注意用户来源内容不应能伪造诊断阶段。
- 诊断写入不能阻塞 stdout/stderr 消费，防止造成死锁或扩大等待。
- 不能为了获取日志而开启 `--verbose`、`--print-traffic` 等高泄露选项。
- 对不支持某阶段的 yt-dlp 或格式，结果是 `unavailable` / `not_observed`，不是 0ms。

### 4.4 计时和任务关联

- Rust 使用 `Instant`，每个 span 有真实 begin/end 与 reason；跨服务事件使用现有 session/trace/task/attempt 关联。
- 前端使用自己的 monotonic clock，不把 JS 与 Rust 的时间戳直接相减。
- 保留异常、取消、超时、进程未输出、下载成功但无 progress 记录等语义。
- 避免重复 stage_started / stage_finished，重复回调不会使负耗时或反向状态。
- `related_trace_id` 应能从首次解析追踪到入队；任务完成时可关联最初 preview。

### 4.5 预期输出

诊断中心可以显示类似（下面数值仅为**示例**）：

```text
下载引擎启动                     4.5ms
等待首次引擎输出                 1600ms
已观察到 before_dl 标记          8400ms
before_dl → 首次有效进度         23000ms
```

不允许把以上示例当成真实结果；实际报告若只测到两个时间节点，就只显示两个。

### 4.6 阶段测试

- 可控假引擎：立即输出、延迟输出、输出标记后延迟进度、无输出、仅 stderr、异常退出、取消、复用旧 attempt。
- 本地原创 HTTP：正常、延迟响应、慢速流、断流 / 超时等。
- stdout/stderr 消费顺序与缓冲行为；较长行和非 UTF-8 安全处理。
- 后处理阶段与无进度的任务不会误标成功。
- 日志白名单、脱敏和体积有界不回退。

**阶段验收：** 至少能把 spawn 后的未知等待分成可证实的子阶段；未能观察到的外部网络部分明确保留未知，不捏造细节。

## 5. 阶段 2：后端可信解析结果缓存与安全回退（P0）

这一阶段需要**实际改进** `enqueue_metadata_recheck` 的成本，但绝不删除其安全目的。

### 5.1 现有安全意图

当前 FluxDL 在预览与入队之间再次使用 Rust + yt-dlp 校验，以防前端自行伪造格式元数据。此规则合理，优化后仍必须保证：

- 后端最终决定可以下载的 URL、媒体模式、格式 ID 与组合。
- 前端传入的标题、格式列表、媒体地址等**不具备授权效力**。
- 保存目录、文件名、参数及引擎路径仍执行原有 Rust 校验。
- 禁止将前端字符串直接拼接 Shell 命令；始终使用可执行文件和参数数组。
- 不能让缓存 token 变成绕过现有 Tauri capability 或后端校验的万能凭据。

### 5.2 推荐缓存结构

第一次元数据解析成功后，Rust 可以在内存中建立有界的 `TrustedPreview`（概念名可调整），例如：

```text
preview_id: 不可预测、不透明的随机 ID
session_id: 当前应用会话
created_at / expires_at: Rust单调时间，避免系统时间调整影响TTL
engine_fingerprint: 当前后端配置 / 引擎可执行文件及有效版本标识
source_identity: 原始来源身份，由后端保存，不在日志中公开
allowed_formats: 来自后端解析的真实可用格式与组合
metadata: 仅业务所需的可信字段
```

约束：

1. 默认仅内存缓存，**不写入 SQLite、JSONL、诊断 ZIP、Git 或 Release**。
2. 初始建议 TTL 为 120–300 秒（先择一测试），容量有严格上限（例如 128 或 256 条）；按需清理过期项，不造成无限增长。
3. 命中仅限相同 Rust 应用会话、有效来源、有效引擎配置及兼容请求；Quick Capture 和 Workspace 都可经受控 IPC 使用相同缓存服务。
4. 用户切换引擎、修改影响提取的配置、应用重启、缓存过期、模式不匹配、格式不匹配或并发状态不一致时，必须拒绝复用并走安全退路。
5. 不能把完整原始 yt-dlp JSON、cookies、headers、signed CDN URL 长期保留；仅保留支持安全复核所需数据，进程退出自动释放。
6. 不能因为缓存存在就跳过存储路径验证、权限限制、格式选择规则和文件名约束。

### 5.3 前后端协议（示意，不强制字段名）

- `parse` 成功时，在原业务响应中附带一个可选 `preview_id` / `trusted_preview_ref`。
- `enqueue` 可传递该 ID 与当前选择的模式 / 格式，但 Rust 仍检查已存的后端可信记录。
- 旧调用者没有 token、来自旧窗口 / 旧会话、缓存未命中时：**走当前完整后端复核路径**，保证功能兼容。
- token 失效、格式无效或不匹配时，不允许静默使用未验证的前端格式；根据现有错误设计决定拒绝或安全重新解析，并给予用户明确反馈。
- 已入队任务的行为完全沿用原业务状态机；不能因重复点击或缓存 race 创建两个相同请求对应的重复任务（遵守当前幂等语义）。

### 5.4 正确性与并发

必须覆盖：

- 首次解析成功 → 在有效期内入队，缓存命中。
- Quick Capture 中解析、Workspace 中入队（如现有 UI 允许相同流程），缓存一致。
- 不同 URL 交叉、随机 token、手写 token、不同 session、过期 token。
- 格式 ID 被篡改、组合不合法、视频/音频模式改变。
- 引擎或影响解析的配置变更、下载目录非法或不可写。
- 解析中被取消、并发解析同 URL、连续快速重复入队。
- 长时间未选择格式后再入队、重启后入队。
- 缓存容量达到上限、过期清理、进程退出后资源释放。
- 缓存成功但下载过程站点格式发生变化：按当前失败 / 重试流程处理，不要错误标记完成。

**重要：** 预览缓存仅消除入队前冗余复核，yt-dlp 实际下载可能仍要重新执行自身的媒体提取。不得声称启用缓存一定消除 spawn 后的 32.95 秒。

### 5.5 诊断必须能判断缓存收益

添加固定白名单字段 / 枚举事件，例如：

- `preview_cache_hit`
- `preview_cache_miss`
- `preview_cache_expired`
- `preview_cache_invalidated`
- `preview_cache_fallback_recheck`

名称可匹配现有 Schema，不要使用任意 `message` 或把 URL 作为键。记录：命中 / 失效原因类别、验证耗时、实际是否发生 yt-dlp 重复元数据提取；不记录 token 或原始来源。

对性能报表，应能比较：

- A：原始完整重新解析。
- B：可信缓存命中时不重新解析。
- Miss / Fallback：回到原有安全逻辑。

### 5.6 开发 / 测试用 A/B 切换

- 为 benchmark 和受控 debug 测试提供 `full_recheck`、`trusted_preview_cache` 两种路径。
- 正式版不暴露危险的「关闭安全校验」开关。
- 开关必须确保覆盖相同业务验证规则。
- 不能在测试路径中修改用户实际设置或生产数据。
- 所有测试使用相同的媒体、同一引擎版本和独立数据目录。

**阶段验收：** 至少证明测试环境中缓存命中减少了第二次引擎元数据提取，并且无缓存与各种异常场景可安全回退；真实收益须在性能对照报告中测量。

## 6. 阶段 3：真实的下载等待状态 UI（P1）

### 6.1 保持视觉基线

完全沿用 Midnight Glass：深石墨、柔和磨砂、银紫强调、低干扰动效。保留 Workspace / Quick Capture、现有侧栏、输入区、下载队列和任务详情布局。

只改进**状态信息**，不进行整体 UI 视觉改版。

### 6.2 状态来源必须真实

允许显示的描述（依照可观察事件择用）：

- `正在校验下载选项`：后端的实际复核开始后。
- `正在等待下载队列`：确实处于 queue wait。
- `正在启动下载引擎`：进程启动期间。
- `下载引擎已启动，正在准备媒体`：已 spawn，但尚未收到更明确的安全阶段信号。
- `正在等待首次有效下载进度`：有对应实际阶段起点。
- `下载中`：收到被当前 attempt 接纳的实际进度。
- `正在进行媒体后处理`：有后处理阶段信号。
- `已完成 / 已失败 / 已取消`：由现有业务终态确定。

只有确实观测到特定下载前标记，才可以显示更具体的含义；不能由经验猜测“正在连接媒体源”“正在获取密钥”“DNS 已完成”等。

### 6.3 UI 细节

- 下载准备阶段显示**已等待时长**，而不是伪造百分比、速度或 ETA。
- 状态应在 Workspace 任务列表 / 任务详情与 Quick Capture 的任务反馈中语义一致。
- 只在确实超出可配置或合理默认的阈值时显示轻量提示：“此步骤等待较久，可查看诊断”。阈值只是用户提醒，不代表故障。
- 一次等待结束后不应残留“正在准备”状态。
- 快速连续状态切换不闪烁，避免在频繁事件中反复重排布局。
- 使用可访问文字 + 图标，不单靠颜色识别状态。
- 现有深浅主题、减少动画偏好和键盘操作必须保持正常。
- 无诊断权限 / 事件缺失时给出明确、安静的降级文案。

### 6.4 精确含义

`first_protocol_progress` 是**协议接纳的首个有效进度**，不等于网络首字节；如果开始下载但未产生可识别进度，UI 只能展示“下载引擎正在运行 / 尚未收到进度”，不能把这个场景判定为失败。

## 9. 阶段 6：性能基线、A/B 实验和优化验收（P0/P1）

这是整个迭代能否称为“性能优化”而不是“代码改动”的判定依据。

### 9.1 三层测试环境

#### 第 1 层：确定性假引擎 / Fixture

测试：

- 立即输出元数据与进度。
- 解析延迟、二次复核延迟。
- spawn 后首个输出延迟。
- before_dl 与 first progress 间隔延迟。
- 无进度成功、无进度失败、stderr 先输出、突然退出。
- 缓存命中、过期、引擎配置失效、错误回退。

目的：验证正确性、事件边界、状态可观察性，不宣称是外部站点性能。

#### 第 2 层：本地原创 HTTP 媒体

继续使用当前 `scripts/test-diagnostics.ps1` / Rust fixture / 本地 WebView2 smoke 的测试资产，必要时加入可控延迟 HTTP 服务器。

要求：

- 每组 20 次以上独立样本用于内部性能比较（资源允许则 30 次）。
- 同一台设备、同一编译模式、相同 yt-dlp 版本、媒体文件、下载参数和数据目录策略。
- A/B 顺序交叉或轮换，避免缓存预热 / 温度 / 资源占用只偏向某个方案。
- 分别记录冷、热路径；不得把缓存命中样本与未命中混为一个数字。
- 结果记录每次成功/失败、超时、阶段缺失、n、p50、p95、max；有失败时单独给出失败率。
- 进行控速/断流场景时不能把预期等待描述为应用实现变慢。

#### 第 3 层：真实外部来源（可选，受环境约束）

- 仅使用获得授权的公开测试媒体以及用户已配置的真实本地引擎。
- 遵守网站条款和请求频率；不要对外部站点开展高频压力测试。
- 真实来源如适用，可以小批量、低频重复采样，并记录足以解释条件变化的**非敏感**环境信息。
- 若无法真实联网或没有可用媒体，记录未测，不得造数据。
- 必须单独解释真实网络的不可控波动，不能把外部延迟和程序开销混为一谈。

### 9.2 最重要的 A/B 指标

至少提供：

| 指标 | A 当前完整复核 | B 可信缓存 | 测量方式 |
|---|---|---|---|
| 首次解析到预览 | 实测 | 实测 | Rust/前端各自单调时间 |
| 入队响应 | 实测 | 实测 | 前端独立时钟 |
| 入队元数据复核 / 信任校验 | 实测 | 实测 | Rust 实际阶段 |
| 是否再次 spawn 提取进程 | 是/否 | 是/否 | 代码路径与真实进程事件 |
| 入队到首次有效进度 | 实测 | 实测 | 已定义的 Rust 阶段 |
| spawn 到首次有效进度 | 实测 | 实测 | 新旧兼容阶段 |
| 下载成功率 / 文件校验结果 | 实测 | 实测 | 真实进程退出和文件核验 |
| 缓存命中率 / 回退次数 | 不适用 | 实测 | 事件统计 |

需要进一步给出绝对差值(ms)、相对差值(%)、n、测试环境和重复步骤。

### 9.3 性能判定原则

- **不设置“必须降低到 3 秒”这类脱离网络条件的硬门槛。**
- 缓存命中应该证明不再次触发冗余后端元数据提取，入队本地成本明显下降；若无收益或出现正确性损害，保留完整复核，报告解释。
- 不能把“单次 7.82s”直接等于缓存节省量；必须经对照实验验证。
- 不允许降低任务成功率、正确选格式、取消 / 重试可靠性、数据持久化和敏感数据保护换性能。
- 端到端成本包含用户可感知的入队等待以及进程启动后的等待；UI 提示本身不能算下载速度提升。
- 要标注哪项指标是**外部引擎/网络主导**、哪项是本程序内部可控。

### 9.4 编写报告

建议生成：

- `docs/engineering/0.2.1-performance-before.md`
- `docs/engineering/0.2.1-performance-after.md`
- `docs/engineering/0.2.1-latency-investigation.md`

如果项目已有可比的报告体系，合并到对应文件即可，避免重复。

这些文档不能包含私有 URL、标题、完整路径、用户凭证、可识别个人信息或完整原始 stderr。

5. yt-dlp 无输出 / 部分输出 / 错误退出。
6. FFmpeg 缺失和需要后处理的情况。
7. 成功退出码 + 真实文件存在才宣告完成。
8. 文件被删除、目标文件夹不可写、磁盘写失败。

12. Release 外部引擎仍允许通过 PATH / 设置选定，不引入自动安装。

### 10.2 新增缓存的安全专项

- token 无法预测或伪造；前端任意 JSON 不会生成可信格式。
- 缓存过期或被清理，不会扩大权限或产生非法任务。

- 不把私人预览数据写入日志、报告、诊断 ZIP 或业务数据库中的额外不必要字段。

### 10.3 新诊断的语义测试

- first output、before_dl、first protocol progress 顺序与已知标记一致。
- 迟到 stdout/stderr / 上一个 attempt 的事件被拒绝。
- 重复标记无重复结束时间。
- 无法观测的阶段为 `unknown/not_observed`，不是 0。
- 没有证据时不显示“网络连接完成”之类推测。
- 日志文件轮转、容量和安全白名单不回退。
- 查询 / 报表不能将不同会话、不同引擎版本的指标不加区分地平均。

## 14. 绝对禁止的捷径

以下任何一种都视为验收失败：

1. 删除二次格式安全复核，而不以 Rust 可信数据和完整校验替代。
2. 前端自己伪造 `preview_id` 对应格式 / URL 的可信结果。
3. 缓存无容量和过期限制；缓存跨重启误用。
4. 缓存了原始含敏感信息的 JSON/URL 并写入日志或公开 ZIP。
5. 把下载命令拼接为 Shell 字符串。
6. 强行开启 yt-dlp `--verbose` / 网络流量日志并保存原文。
7. 在未验证 flag 语义的情况下用 `--print` 破坏实际下载流程。
8. 把“首次有效进度”写成“首字节已下载”或“连接已完成”。
9. 用前端定时器伪造实际引擎阶段、进度、速度或预计剩余时间。
10. 将 1 次真实网络样本的 p95 说成一般性能结论。
11. 测试 A/B 时把不同网络条件下的结果做不加说明的直接比较。
12. 为了加快下载关闭 TLS 证书校验、跳过错误分类或绕过站点限制。
13. 拆掉原有 SQLite/IPC/诊断系统重新造一套。
14. 意外改动 Midnight Glass、双窗口设计、历史、托盘行为或用户数据。
15. 构建失败先删除上一版 `release-output`；自动清空编译缓存或开发日志。
16. 把调试日志、诊断包、测试媒体或私人数据提交到公开 GitHub。
17. 只输出“我已经优化 xx%”而不提交可复现的测试数据。

## 15. 最终验收标准

下面这些都需要逐项答复“通过 / 失败 / 未测试”并给证据：

### A. 定位能力

- [ ] 下载 spawn 后至少增加一类经过验证的可观察阶段。
- [ ] `download_first_progress` 仍保持严格语义。
- [ ] 无法确定的网络内部等待明确保留未知。
- [ ] 任务 Trace、Attempt、Session 关联正确。

### B. 性能与安全

- [ ] 首次预览产生 Rust 可信、短时、有界的缓存引用。
- [ ] 缓存命中时真正减少不必要的入队元数据二次提取。
- [ ] miss/expired/config-change 等场景安全回退。
- [ ] 前端提交的 URL / 格式 / 路径不会绕过原后端安全校验。
- [ ] A/B 数据量、测量条件和实际结果完整记录。
- [ ] 下载成功率、文件格式正确性、取消/重试没有回退。

### C. UI 与诊断

- [ ] Workspace 和 Quick Capture 的等待状态来自真实事件。
- [ ] 已等待时长真实，没有虚构百分比或 ETA。
- [ ] 任务详情可以直达关联诊断 Trace。
- [ ] 能复制安全的任务诊断摘要。
- [ ] 旧日志和未知阶段被正确识别；深浅主题正常。

### D. 工程与发布

- [ ] 前端和 Rust 检查、测试、诊断专项与 smoke 已按环境实际运行。
- [ ] 历史 SQLite/IPC 与原下载行为兼容。
- [ ] 诊断继续轮转、脱敏、不自动上传。
- [ ] 代码版本可在新报告中明确关联，无法取得时标未知。
- [ ] 现有 `release-output/FluxDL/` + `FluxDL.zip` 工作流无回退。
- [ ] Git 交付按 `AGENTS.md` 的当前用户授权执行，远程状态如实核实。

## 16. 交付报告格式：必须有实际结果而不是口号

完成后给出下面结构的报告，可写入 `docs/engineering/0.2.1-validation-report.md` 并在 Codex 回复中简述：

### 16.1 代码与版本

- 本次实际 HEAD（短 / 完整 SHA）、工作分支、应用版本。
- 修改过的文件与新增模块。
- 真实检查过的引擎和依赖版本。

### 16.2 根因调查

- spawn 至首次进度中**真正可证明**的各阶段耗时。
- 无法进一步解释的剩余时间，原因及证据不足之处。
- 首次解析、复核和下载进程自身解析各自的职责。

### 16.3 缓存与安全

- 缓存策略、TTL、容量、失效条件、命中率。
- 是否确实免去一次重复提取。
- 缓存命中 / 未命中 / 失败回退的实际行为。
- 安全专项和兼容性测试结果。

### 16.4 性能数据对照

必须有如下表格（只填实际测量值，未测标注“未测”）：

| 指标 | 旧实现 p50 | 新实现 p50 | 旧实现 p95 | 新实现 p95 | n 与环境 | 改善 / 回退 |
|---|---:|---:|---:|---:|---|---|
| 首次解析到预览 | | | | | | |
| 入队响应 | | | | | | |
| 入队安全复核 | | | | | | |
| 入队到首次有效进度 | | | | | | |
| spawn 到首次有效进度 | | | | | | |
| 下载成功 / 失败 | | | | | | |

不能混用不同来源、不同测试条件或“用户单次 7.82s”与“本地 20 次平均值”进行没有说明的比较。

### 16.5 验证命令和结果

逐条列出真实执行的命令、通过 / 失败 / 跳过数、测试环境，以及任何未验证的 Windows 原生场景。

### 16.6 风险与下一步

按 P0/P1/P2 列出剩余问题，例如：外部网络与站点慢、缓存过期率、未覆盖的 yt-dlp 版本差异、缺失真实网络采样。

### 16.7 Git 与正式产物

说明提交、推送、远程 SHA、工作树状态及是否执行正式 Release 构建；只有真的执行并验证后，才能附带本地产物位置。遵守用户已授权的仓库协作流程，不擅自创建 GitHub Release。

## 17. 立即开始执行

现在从当前 FluxDL 工程开始，执行如下工作：

1. 阅读项目规范、现有工程记忆、诊断设计和测试文档。
2. 检查实际源码 / 当前 Git HEAD / 现有 `dev-logs`；校验上传的单次样本与当前日志是否对应。
3. 建立审计文档、可控 Fixture 与基线数据。
4. 实现下载引擎启动后可证明的细粒度计时。
5. 实现带安全准入、失效和回退的 Rust 可信解析缓存。
6. 实现真实等待状态、任务诊断跳转和安全摘要复制。
7. 为报告加入代码 revision 等安全构建元数据。
8. 运行 A/B 基准、故障注入、真实下载 smoke、UI / 类型 / Rust / 诊断回归。
9. 根据真实结果修复已确认的瓶颈；不为达成速度数字降低可靠性。
10. 更新项目文档、工程记忆、按仓库已授权规范交付代码，写出完整验证报告。

最终要达到：**减少可避免的重复解析；清楚解释无法避免的下载准备等待；所有优化都有证据，且下载安全、数据正确性和既有 UX 不回退。**
