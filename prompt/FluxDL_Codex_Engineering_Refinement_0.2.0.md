## 0. 你的角色与最终目标

你是一名资深桌面应用工程师，熟悉：

-   React、TypeScript、Vite、Zustand
-   Tauri 2、Rust、异步任务与子进程生命周期管理
-   SQLite、事务、数据库迁移和持久化一致性
-   桌面应用 IPC、多窗口状态同步
-   前端组件架构、自动化测试、性能分析和工程化规范

你正在维护的是 **FluxDL**：一款基于 Tauri 2、React、Rust 和 yt-dlp 的
Windows 桌面下载应用。项目已经完成第一版
MVP，并有真实的下载、解析、任务队列、历史记录、双窗口、托盘和主题等功能。

本轮目标不是增加功能数量，而是让现有实现更容易理解、更安全、更高效、更容易测试，也更适合后续持续使用
Codex 进行迭代。

### 本轮核心目标

1.  建立可靠的测试与性能基线，确保后续重构可验证。
2.  将过于集中的 React 页面、状态和样式逐步模块化。
3.  改善 SQLite 持久化：增量写入、缩短锁持有时间、明确数据一致性。
4.  改善 Tauri IPC 与双窗口状态同步：减少不必要的全量快照和 UI
    更新，正确处理乱序、丢失和过期事件。
5.  将 Rust 任务管理、下载引擎、子进程管理、事件和持久化职责合理拆分。
6.  保持现有用户行为、数据兼容性、窗口体验和视觉风格。

### 成功标准

重构完成后，用户仍然使用熟悉的 FluxDL：

-   Quick Capture 和 Workspace 仍然正常工作。
-   yt-dlp 解析、下载、取消、重试、历史记录等现有功能不回退。
-   下载进度、完成、失败、取消和后台任务状态可靠。
-   SQLite 数据不会因重构而丢失，旧数据库能够继续使用。
-   两个窗口始终展示一致且不过期的任务状态。
-   前端和 Rust 代码职责更清楚，测试覆盖更完整。
-   能通过仓库现有的构建、测试、格式和静态检查。

## 6. 阶段 3：SQLite 持久化与任务管理优化

这是本轮最高优先级的架构改进之一。请仔细分析后再实施。

### 6.1 先明确状态源和一致性边界

明确：

-   内存任务管理器是运行时任务状态的权威来源。
-   SQLite 是可恢复的持久化来源。
-   前端是展示层，不应成为任务状态权威来源。
-   不应在持有任务队列状态锁时执行慢速数据库 I/O。
-   不应让进度高频写入阻塞子进程读取或其他任务操作。

在文档中说明任务从创建到完成的状态流转和持久化时机。

### 6.2 将整表重写改为增量持久化

如果当前实现仍然采用整表删除再重写，请改为按任务变更进行增量写入：

-   新任务：INSERT。
-   已有任务变化：UPDATE 或 UPSERT。
-   用户明确删除任务：DELETE 对应记录。
-   不因单条任务进度变化而删除和重建所有任务。
-   需要多条记录一致更新时使用事务。
-   对常用查询字段建立必要索引，但不要过度索引。
-   保留现有任务排序和历史行为。

使用现有 SQLite crate 和连接管理方案，避免无必要地更换数据库库。

### 6.3 不允许在任务状态锁内执行数据库 I/O

检查所有数据库调用路径，包括：

-   新增任务。
-   进度更新。
-   暂停 / 取消（如果当前已有）。
-   完成。
-   失败。
-   重试。
-   删除。
-   应用启动恢复。
-   应用关闭。

设计清晰的锁边界：

1.  获取任务状态锁。
2.  更新内存状态并生成需要持久化的变更数据。
3.  释放任务状态锁。
4.  再进行数据库操作或发送持久化请求。
5.  将持久化结果以明确方式反馈给任务管理器。

不要通过简单地把所有锁改成 `RwLock` 来掩盖锁竞争问题。

### 6.4 持久化写入调度

优先考虑一个职责单一的持久化 worker / 写入队列：

-   数据库连接由明确的所有者管理。
-   写入顺序可预测。
-   同一任务的旧版本写入不能覆盖新版本。
-   高频进度可以合并或节流。
-   任务创建、完成、失败、取消、删除等关键变化必须有可靠的持久化保障。
-   应用关闭时应有 flush / drain 机制。
-   写入失败必须记录、可诊断，并提供合理重试策略。
-   不允许静默丢弃终态。
-   不要在数据库失败时假装持久化成功。

如果当前 SQLite 连接类型不是
`Send`，应采用与现有运行时兼容的单线程数据库 worker 或合适的 blocking
边界，不要强行跨线程共享不可安全共享的连接。

### 6.5 进度节流与终态优先

进度更新频率可能远高于任务状态变化。

建议：

-   进度事件与数据库写入分开考虑。
-   高频进度允许按时间窗口合并。
-   每个任务的最新进度应能在合理时间内落库。
-   完成、失败、取消等终态变化必须触发强制 flush 或持久化确认。
-   终态之后到达的旧进度不得覆盖终态。
-   应用退出时，等待关键写入完成；等待必须有合理超时和失败报告。

不要为了减少写入而让用户看到已完成但重启后变成下载中的任务。

### 6.6 事务与数据库迁移

-   检查当前 Schema 和历史数据格式。
-   使用现有迁移方式；如果没有可靠版本管理，再引入最小的 Schema
    版本机制。
-   优先使用 SQLite `PRAGMA user_version`
    或当前项目已采用的迁移表，不要重复建立多套版本系统。
-   每次迁移在事务内执行。
-   迁移必须有明确的前后版本。
-   迁移失败时回滚。
-   旧版本数据库必须可以继续读取和迁移。
-   不删除未知字段或用户已有记录。
-   不因新增枚举类型而破坏旧字符串数据。
-   不擅自重置数据库。

WAL、同步等级、busy timeout
等参数应根据当前实现和测试结果决定。不要不经测量就修改 durability 配置。

### 6.7 数据模型与序列化兼容

如果需要将字符串状态改为 Rust enum：

-   保留现有 JSON / SQLite 序列化兼容性。
-   明确 `serde` 的命名规则。
-   对历史未知值提供兼容处理或安全降级。
-   对用户自定义格式、参数和路径保留字符串表达能力。
-   不要让旧任务因为无法反序列化而整体加载失败。

### 6.8 文件存在性检查

如果当前快照生成或任务列表更新会频繁检查文件系统：

-   不要在每一次进度更新时重新检查所有历史文件。
-   将文件存在性检查移到历史页面加载、详情请求或合理的缓存刷新流程。
-   保留用户看到的文件可用 / 不存在状态。
-   不要在主任务状态锁内执行大量文件系统 I/O。

### 6.9 SQLite 测试要求

至少验证：

-   旧数据库迁移。
-   增量写入。
-   同一任务快速连续更新。
-   多任务交错更新。
-   旧版本写入不能覆盖新版本。
-   终态不能被迟到的进度覆盖。
-   写入失败后的错误路径。
-   事务回滚。
-   关闭前 flush。
-   1,000 / 5,000 条历史任务下的加载和更新表现。

### 6.10 阶段验收

-   不再因单条任务更新而全表删除重写。
-   数据库 I/O 不占用任务状态锁。
-   终态持久化可靠。
-   旧数据库和历史记录保持兼容。
-   数据库错误可以被诊断。
-   性能测试与基线进行对比，并记录实际结果。

## 7. 阶段 4：Tauri IPC 与双窗口状态同步优化

目标是让 Workspace 和 Quick Capture
共用同一份权威状态，同时避免高频全量快照广播。

### 7.1 先保留完整 Snapshot 的价值

完整 Snapshot 仍然有用，适用于：

-   应用初始化。
-   新窗口启动。
-   前端发现事件丢失。
-   前端状态不可信时重新同步。
-   开发诊断。

不要为了追求增量事件而删除完整 Snapshot 能力。

### 7.2 高频更新改为增量事件

根据实际数据模型设计事件类型，例如：

-   `TaskCreated`
-   `TaskUpdated`
-   `TaskProgress`
-   `TaskRemoved`
-   `QueueSummaryUpdated`
-   `SettingsUpdated`

以上只是语义示例，应根据现有事件协议整合，不要为了拆事件制造大量重复结构。

事件应该只包含该次变化所需的数据。不要在每次进度更新时广播全部任务、完整日志和全部媒体元数据。

### 7.3 事件版本与乱序保护

设计明确的事件 envelope，至少考虑：

-   `session_id` 或等效运行会话标识。
-   单调递增的 `revision` / `sequence`。
-   事件类型。
-   任务 ID（适用时）。
-   变化数据。

具体字段命名可以遵循当前项目风格。

要求：

-   前端拒绝旧版本事件。
-   同一事件重复到达时不会重复产生副作用。
-   任务进度不能倒退。
-   终态不能被较旧事件覆盖。
-   发现事件序列缺口时，触发完整 Snapshot 重新同步。
-   不同应用运行会话之间的旧事件不能污染新状态。

### 7.4 初始化订阅竞态

重点处理"先取 Snapshot 还是先监听事件"的竞态。

采用可靠策略，例如：

1.  注册事件监听。
2.  请求带 revision 的完整 Snapshot。
3.  将 Snapshot 与监听期间收到的事件按 revision 合并。
4.  只有较新的状态才能覆盖当前状态。

或者采用经过验证的等效机制。

必须测试：

-   监听刚注册就收到事件。
-   Snapshot 请求期间收到新事件。
-   Snapshot 返回时已经存在更新的前端状态。
-   事件乱序和重复。
-   事件缺失后重新同步。

### 7.5 前端增量 Store 更新

-   任务事件按 task ID 更新对应任务。
-   不要每次进度更新都替换整个 AppSnapshot。
-   不要让无关页面订阅全部任务进度。
-   对高频事件采用合理的 UI 更新节奏。
-   事件节流不能丢失最终状态。
-   日志可以采用增量追加或按需读取，避免反复发送完整日志。
-   保留任务详情按需获取的能力。
-   Store 的更新逻辑应尽可能可测试、可独立运行。

### 7.6 两个窗口的一致性

-   Workspace 和 Quick Capture 都订阅同一套事件协议。
-   窗口隐藏、显示、销毁和重新创建时正确注册 / 清理监听。
-   不允许一个窗口维护独立且冲突的任务真相。
-   新窗口启动时获取最新 Snapshot。
-   一个窗口关闭不能影响后台任务或另一个窗口的状态。
-   任务状态更新不依赖某个特定窗口存在。

### 7.7 事件性能与节流

-   根据实测设置进度事件频率。
-   不要无意义地以极高频率广播。
-   合并相邻、过时的进度变化。
-   创建、完成、失败、取消、删除等语义事件不可被普通进度节流吞掉。
-   不要在事件发射过程中持有长时间状态锁。

### 7.8 阶段验收

-   两个窗口状态一致。
-   初始化竞态有测试覆盖。
-   过期事件不能覆盖新状态。
-   高频进度更新不会导致全量快照持续广播。
-   事件丢失可以通过 Snapshot 恢复。
-   前端只更新受影响的状态范围。

### 8.1 模块职责

``` text
  diagnostics/
    mod.rs
```

如果项目已有成熟的模块组织方式，优先渐进式整理现有结构。

### 8.2 Queue / Manager

任务管理层只负责：

-   创建任务。
-   维护任务状态。
-   校验状态转换。
-   管理任务 ID 和顺序。
-   协调引擎、进程、持久化和事件。
-   处理取消、重试和完成等生命周期。

不要让 Queue Manager 直接负责：

-   拼接 yt-dlp 命令。
-   解析所有 stdout / stderr 文本。
-   执行数据库 SQL。
-   直接构建前端事件 JSON。
-   执行长时间文件系统操作。

### 8.3 Engine

引擎层负责：

-   yt-dlp 参数构建。
-   元数据解析命令。
-   下载命令。
-   进度模板解析。
-   错误信息归类。
-   FFmpeg 相关参数和后处理信息。

命令必须通过参数数组传递，不允许拼接 Shell 字符串执行。

构建参数应是可单元测试的纯逻辑或低副作用逻辑。

### 8.4 Process

进程层负责：

-   启动子进程。
-   管理 stdout / stderr 读取。
-   处理退出码。
-   取消和终止。
-   等待子进程退出。
-   清理读取线程和资源。
-   避免孤儿进程和重复终止。

重点审查取消与完成之间的竞态：

-   用户取消时进程刚好完成。
-   进程失败时用户同时点击重试。
-   子进程已经退出但读取任务尚未结束。
-   任务终态已经设置，但迟到的进度回调仍然到达。

同一个任务只能产生一个确定的终态。重复取消、重复完成和重复清理必须安全、幂等。

### 8.5 状态机

将当前任务状态转换规则整理为清晰的状态机。

可以参考：

``` text
Queued
  -> Resolving
  -> Downloading
  -> PostProcessing
  -> Completed

Resolving / Downloading / PostProcessing
  -> Failed
  -> Cancelled
```

实际状态必须以当前产品实现为准。

要求：

-   只允许合法状态转换。
-   状态转换集中处理。
-   终态不能被普通进度事件覆盖。
-   重试必须生成明确、可追踪的状态变化。
-   不要宣称支持真实暂停 / 续传，除非当前底层确实实现并经过测试。
-   前端状态标签与 Rust 状态含义一致。

### 8.6 强类型与兼容性

适合使用 enum 的内部状态可以逐步改为强类型：

-   TaskStatus。
-   任务处理阶段。
-   解析结果类型。
-   错误类别。

但必须兼容旧数据和旧 IPC 格式：

-   保持 JSON 字段命名兼容。
-   对历史未知枚举值提供兼容策略。
-   用户自定义参数和格式 ID 仍允许字符串。
-   不要为强类型而破坏 SQLite 中已有任务。

### 8.7 日志与安全

-   不记录 Cookies 内容。
-   不记录认证 Header。
-   对代理 URL 中的用户名和密码脱敏。
-   对可能包含凭据的命令参数进行日志过滤。
-   不把敏感参数传给前端日志面板。
-   保留足够的诊断上下文，例如错误类别、退出码、任务 ID
    和安全的命令阶段。
-   不通过 Shell 拼接命令。
-   不扩大 Tauri capability 权限。

### 8.8 错误处理

-   使用清晰的内部错误类型。
-   在 Rust 内保留错误上下文。
-   IPC 返回给前端时转换为稳定、可理解的错误结构。
-   不把所有错误都转换成同一个字符串。
-   不吞掉子进程读取、数据库和事件发射错误。
-   不因一次日志读取异常而静默丢失任务终态。

### 8.9 阶段验收

-   Rust 模块职责清晰。
-   任务状态转换集中且有测试。
-   子进程取消与清理可靠。
-   命令参数构建可测试。
-   日志脱敏。
-   不破坏旧任务数据和前端 IPC 兼容性。

## 13. 明确禁止的重构方式

以下做法不允许：

1.  一次性重写整个 App.tsx 或整个 Rust Manager。
2.  为了目录整齐而移动大量文件，却没有职责改善。
3.  将数据库操作简单包装一下，但仍在任务状态锁内执行。
