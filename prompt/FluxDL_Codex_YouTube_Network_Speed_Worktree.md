# FluxDL — YouTube 下载速度专项诊断与优化 · Codex 自主执行任务书

> **用途**：将此 Markdown 文件直接交给在 **Windows 本地 FluxDL 临时 Git Worktree** 中运行、能够访问本机 Clash Verge / yt-dlp 的 Codex。要求 **Codex 自动检查、自动测试、自动分析、按证据修改、自动复测**，而不是给用户一份需要手工执行的教程。
>
> **仓库**：https://github.com/DewMysimple/FluxDL
>
> **当前症状**：用户通过 Clash Verge 已开启代理和 TUN 虚拟网卡，但 FluxDL 下载部分 YouTube 视频速度长期大约 `100 KB/s`（注意确认 `KB/s` 与 `kb/s`）；其他网络应用没有如此明显的慢速。
>
> **本轮隔离要求**：工作只在用户**已存在的临时 Worktree / 当前功能分支**内进行；主线承担另一轮以诊断数据为基础的优化，本专项不要动 `main`、不要合并、不要重做 UI / 现有诊断架构。
>
> **用户意图**：**我不想自己打开命令行测试、不想切换 Clash 节点、不想手工观察速度。请你尽可能独立完成一切能自动化的检查与测试。**

## 0. 任务目标与成功条件

你是一名熟悉 Windows 网络栈、Clash Verge / Mihomo、TUN、HTTP/SOCKS5 代理、YouTube 媒体 CDN、yt-dlp、Tauri 2 / Rust 子进程和高频下载诊断的高级工程师。

本次的核心任务是确定：

**为什么使用 FluxDL 下载 YouTube 时只有约 100 KB/s，而其他网络使用正常；是否是路由/代理、媒体 CDN、格式协议、yt-dlp 命令或 FluxDL 实现导致；如何以安全且可复现的方式提高速度。**

**你必须完成以下闭环：**

1. 在当前 Worktree 审计实际代码、Git 保护边界、诊断日志和外部引擎。
2. **自动**读取本机可安全获取的网络环境事实，确认 Clash 本地监听、系统代理、TUN 状态、环境变量与实际下载进程参数的关系；不猜端口。
3. 使用安全、有限、可控的自动对照测试：FluxDL 原样配置 vs 相同设置下 yt-dlp CLI vs 显式 Clash 本地代理（必要时再测同一格式的小幅并发变化）。
4. 区分“解析慢 / 二次校验慢 / 排队慢 / spawn 后待进度慢 / 持续下载速度慢”，不要拿整个任务耗时当网络吞吐。
5. 基于实测定位最可能的瓶颈。**只在证据充分时**实施最小、可回退的修复或可选网络设置。
6. 自动复测，输出前后数据、协议、网络路由证据、测试限制和结论。
7. 保留主线现有诊断中心、隐私规则、下载安全、SQLite、Quick Capture、Workspace 和 release-output 构建流程。

**不得虚构速度提升、无法控制的节点切换结果、浏览器/Clash 页面截图或真实 YouTube 测试结果。**

## 2. 本机网络与代理环境：只读自动发现，不要求用户操作

### 2.1 安全获取可验证事实

在 Windows 本机进行只读检查，例如：

- 当前 yt-dlp、FFmpeg、可用 JS Runtime 的可执行文件位置、版本、可用性（不自动升级）。
- Clash Verge / Mihomo 是否在运行；本地 HTTP / Mixed / SOCKS 代理端口是否正在监听、协议是否可确认。
- 当前系统代理、`HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY` 环境变量是否生效；注意大小写和继承给 Rust 子进程的环境。
- TUN 是否启用、虚拟适配器/默认路由是否可见（只读，不关闭）。
- Windows IPv4/IPv6、DNS 解析与目标域名到连接的基本特征；避免大量 DNS 扫描。
- 是否存在与 Clash 同时运行的其他 VPN、代理链或可能冲突的虚拟网卡；只报告，不自行禁用。
- 若已有可信、授权且本地可访问的 Mihomo 控制器 API，可只读查询 `googlevideo.com` 等媒体连接的匹配规则和出站信息；**不得读取、展示、上传控制器密钥、订阅地址、代理认证信息或节点私密配置**。

如果无法自动确认端口，可以通过 Clash 的**进程/本地监听**进行交叉核实；不要直接把 `7890` 或 `7897` 硬编码为正确端口。若只有一个可确认的本地 loopback mixed 代理，可优先测试它；多个候选时执行有限的本地连接验证并记录结果。

### 2.2 重要安全约束

- **不修改 Clash Verge 配置、不切换节点、不重启 Clash、不改变 TUN、不修改系统代理、不刷新 DNS 缓存、不修改防火墙/注册表、路由表或网卡**。
- 不通过读取订阅源或隐私配置来寻找“最快节点”；不遍历用户的节点列表，也不滥用 Clash 控制 API 写接口。
- 不打印完整代理地址（若包含账号密码）、完整远程媒体签名 URL、Cookies、系统用户名及本地隐私路径。
- 允许**仅对本次启动的 yt-dlp 子进程**使用 `--proxy` 指定已验证的 `127.0.0.1` 代理端口作对照实验；不修改全局代理设置。
- TUN 已开启的情况下，显式代理与 TUN 两种调用**不一定代表两个独立物理出口**，结论只能基于真实连接/规则证据，不能仅凭 CLI 参数断言一定走不同节点。

### 2.3 形成一份脱敏环境快照

写入（ignored 测试目录）：

```text
artifacts/network-diagnostics/<run-id>/environment.safe.json
```

只包含：Windows 版本、yt-dlp 版本、代理模式、是否发现本地监听、端口和协议类别、TUN 是否可确认、运行模式、时间和脱敏判断。端口信息本身可保留，任何控制器密钥与真实 URL 不得落盘。

## 3. 自动测试：不依赖用户手工跑命令

### 3.1 测试素材与授权

优先选择用户**已经在 FluxDL 主动下载/测试过、且有权用于排查**的 YouTube 单视频链接；如果可以从当前 Worktree 对应的隔离开发数据或现有可用任务中取得，则**仅在内存中取用**，不在新日志、JSON、报告、Git 或命令行展示中写入完整 URL。不得改动用户原下载文件、历史数据库或已有任务。

如果没有明确适合的 URL：

1. Codex 可以自主寻找明确许可复制/下载、非 DRM、无需登录的公开 YouTube 测试素材，但必须核实授权来源，而不是因为“公开可观看”就认定可以批量下载。
2. 优先用 `yt-dlp --skip-download` / `-F` 完成不下载的诊断，并使用已有仓库中**有明确许可**的 Blender Foundation 测试媒体进行普通 HTTPS 传输基线。
3. 若最终无法取得有权使用的 YouTube 测试 URL，**不要凭空编造真实 YouTube 吞吐结果**；完成所有本地、离线与非 YouTube 对照，报告 YouTube 实测未完成的具体原因。不要要求用户手动测试或贴一大堆终端输出。

需要避免保存或打印 `googlevideo.com` 上的带签名媒体 URL；也不要绕过 DRM、付费内容、登录或访问限制。

### 3.2 预算与自动停止

为了不让测试无限下载大文件、耗尽流量或占用磁盘：

- 所有真实视频测试保存到 **本 Worktree 的 ignored 临时目录**，例如 `artifacts/network-diagnostics/<run-id>/downloads/`。
- 单轮测试最长约 30–45 秒，单轮实际传输约 30–50 MiB 上限；**整次测试总流量默认预算不超过约 300 MiB**，应由测试执行器主动监管并终止其自己启动的测试进程树。
- 限制测试组数，够判断原因即可停止；下载速度极慢时不反复重试几十次。
- 显式设置合理超时、重试次数和短暂预热；不要使用无限 `--retries`，不要启用高并发爆破。
- 任务未完成测试文件只允许删除本次测试专用目录下的内容；不得清理用户实际下载目录或发行版数据。
- 若测试服务器请求拒绝、403 / 429 或出现明显限流/封禁信号，立即降低负载或停止，不绕过访问控制、不反复切客户端伪装规避限制。
- 不更改 TUN、节点和系统代理；不安装额外下载器、浏览器扩展或内核驱动。

**非常重要：** 不能将 `--simulate` 或 `--skip-download` 的成功当作下载速度证明。真实吞吐测量必须基于实际有效下载的数据进度。也不能只看刚启动的 0.5 秒瞬时峰值。

### 3.3 默认实验矩阵（自动、有界）

先完成一次明确的“格式/协议”预检查，拿到视频实际 format ID、协议、是否 segmented/DASH/HLS、是否包含独立音视频轨，再固定**同一个真实格式**进行对比：

| 序号 | 对照方案 | 目的 | 是否修改用户代理 |
|---|---|---|---|
| A | FluxDL 现有下载流程（隔离数据与目标目录） | 还原用户体感速度与真实参数 | 否 |
| B | yt-dlp CLI，尽量与 FluxDL 等价的参数、同引擎、同格式 | 检查 GUI/Rust 实现是否额外影响吞吐 | 否 |
| C | yt-dlp CLI，相同格式，显式 `--proxy` 指向确认存在的 Clash 本地代理 | 比较应用默认网络路径与显式代理 | 否 |
| D（条件满足才测） | CLI 在同一代理下 `-N 4` | **仅实际 DASH/HLS 分片协议**检查并发收益 | 否 |
| E（可选） | CLI 在同一条件下有限改变 `--http-chunk-size` | 仅在速度曲线/协议证据提示可能有价值时作小规模实验 | 否 |

如果 A 阶段完整 GUI 自动化成本高，可复用当前 Rust 生产引擎 / Manager 的 headless integration harness，而不是 Mock 整条链路；必须明确说明与 GUI 路径的差别，并至少检查 GUI 实际构建参数与 B/C 的差异。

如需每轮多次采样，保证同一格式、同一 URL、同一代理模式、相似采样时间和同等缓存条件；可以交替顺序 A/B/C，降低时间变化造成的偏差。真实 Internet 的波动不可视为完全可控。

**不能把不同分辨率、不同码率、不同视频、不同协议直接放入同一列去比较“下载器快慢”。** `-N` 并非普通单连接 HTTPS 下载加速器；如格式不支持分片，则跳过，不冒充失败。

### 3.4 应自动收集的指标

每次实验写入一组**脱敏**记录：

- 实验编号、条件、样本数、引擎版本、格式 ID 或非敏感格式概要、协议类别。
- `duration_s`（有效下载时长）、`downloaded_bytes`（真实传输进度）、`mean_Bps`、`median_5s_Bps`、`last_10s_Bps`、`max_Bps`（可用时）。
- 首次进度耗时、停滞次数与停滞时长、重试/HTTP 错误统计（仅可可靠获取时）。
- 格式是否为单个 HTTPS 媒体、分片/DASH/HLS、外部下载器、音视频分离；用户的下载与后处理耗时不能混入网络速度。
- 代理模式（TUN/未知/显式 local proxy）、对应本地端口与连接路由证据（可靠取得时）。
- 命令行参数**白名单概要**，不要存储原始完整命令行、下载 URL、Cookie 或签名媒体链接。
- 系统 CPU/内存/磁盘吞吐简要指标（仅当可用，作为排除本地瓶颈的辅助证据）。

速度单位统一保留 `KiB/s` 和 `MiB/s` 或明确标注 MB/s 的十进制换算，避免把 `100 kb/s`、`100 KB/s` 和 `1 MB/s` 混淆。

对每一次实验明确标注是 **实际 YouTube 测试**、**Blender 普通 HTTPS 控制组**、**本地 fixture** 还是 **只解析不下载**，不得混用结果。

## 5. 判断原因：有证据才优化

请根据实验数据进行有区分度的判断：

| 现象 | 优先怀疑 | 下一步 |
|---|---|---|
| FluxDL 和等价 yt-dlp CLI 都慢 | Clash 出口、YouTube CDN、yt-dlp/格式/协议 | 看显式代理与格式证据 |
| FluxDL 慢、等价 CLI 明显快 | 应用参数、环境变量、子进程/进度路径 | 比较实际 argv/env、定位代码差异 |
| 显式本地代理明显快 | 默认路由/系统代理继承存在差异 | 给 FluxDL 增加可选显式代理并复测 |
| 多个协议/节点观测到固定低速 | 媒体 CDN、服务端策略或提取方法 | 查引擎输出、重试、格式，不简单加线程 |
| `-N 4` 只在 DASH/HLS 上有效 | 分片并发配置存在可选价值 | 作为可配置实验项，不全局强制 |
| 初次解析耗时很长但下载稳定快 | 提取/二次安全复核 | 属主线诊断方向，不误判为带宽慢 |
| spawn 后迟迟无首次进度 | 引擎连接/提取/资源协商 | 增加可信阶段证据，而非伪造“连接中” |
| CPU、磁盘异常繁忙 | 本地 I/O/后处理限制 | 单独测下载阶段与 FFmpeg 阶段 |

**不得仅因“其他网站很快”就断定 YouTube 一定被限速；也不得只因开了 TUN 就断定 yt-dlp 正在走预期的 Clash 节点。**

如果 Clash 代理节点/线路明显成为瓶颈，且你没有安全、可授权的自动切换权限：

- 不自行切换节点或修改规则。
- 在报告中给出证据，指出优化代码可能无效。
- 用户要求无需亲自测试，所以**仍应自动完成能够做的代码层诊断、测试脚本与可选显式代理适配**；只有确实必须由用户选择节点时，才把它列为外部阻塞，不推诿为“请用户先手测”。

## 6. 允许的最小代码优化（满足证据条件才执行）

### 6.1 FluxDL 显式代理支持（如果实验证明有必要）

如现有代码缺少显式代理或 CLI 明显快于 FluxDL，则在保留默认行为的前提下添加安全、克制的设置：

- 默认：`跟随当前网络环境（TUN/系统网络）`，原用户行为保持不变。
- 可选：`本地 HTTP 代理` / `本地 SOCKS5 代理`，地址只能由明确配置指定；提供对 `127.0.0.1`/`localhost` 端口的安全检测反馈；必要时允许经过校验的本地 URL。
- 不自动将检测到的 Clash 代理写回系统，不改变 Clash 配置。
- yt-dlp Rust 参数以**参数数组**安全传入 `--proxy`；下载、解析、二次复核应使用一致、经过验证的网络配置，防止解析成功但下载走错路。
- 若已有设置类型/数据库，请使用兼容性迁移和持久化，不能破坏旧设置或任务历史。
- UI 延续现有设置页风格，不新增大量网络参数或独立页面。
- 不能把带凭据代理串记录进日志、SQLite 明文或导出包；若当前架构不能安全保存认证信息，MVP 仅支持本地无凭据代理并明确标注。
- 显式代理配置失败时提供错误与回退途径，不可静默假装已代理。

如果显式代理不能带来稳定收益，不必强行增加设置；保留自动化对照结果即可。

### 6.2 分片并发与 HTTP chunk（仅实验有证据时）

- `--concurrent-fragments`（`-N`）只在**协议支持**的情况下启用，默认维持原行为，可提供 1/2/4 级实验配置；不全局默认设置 16/32。
- `--http-chunk-size` 是实验性选项，不可当作通用加速器；若未显著改善、失败增多或增加数据开销，应保持关闭。
- 不能通过切换格式/降低画质、隐性丢弃音轨来制造“速度更快”的错觉。
- 不强制添加 aria2c、下载器伪装、Cookie 抓取、PO Token 绕过或违反访问控制的行为。
- 如现有 yt-dlp 版本存在兼容性警告，可提供更新建议和证据，但未经授权不偷偷更换用户已有的可执行文件。

### 6.3 健壮性

- 对重试、超时、进度缺失、部分下载文件、取消进程树进行边界测试。
- 必须区分“网络问题”和“二次解析/队列等待/后处理”问题。
- 网络设置和吞吐诊断不能导致下载、取消、历史、双窗口 IPC、SQLite 和 release-output 流程回归。

## 8. 测试与验收标准

### 自动化测试必须覆盖

- 代理端口探测正确/错误/多个候选，均不读取或泄漏控制器 Token。
- TUN 可见但实际路由不确定时，报告“不确定”而非强行认定“已走代理”。
- 同一引擎与格式的 CLI/FluxDL argv 等价性（允许应用必要的安全参数）。
- 配置显式 HTTP/SOCKS5 代理时 Rust 参数构建正确；参数值不经 Shell 拼接。
- 5s/10s 吞吐统计计算、KB/s 与 kb/s 换算。
- 进度缺失、未知总量、下载开始/结束、FFmpeg 后处理时正确计时。
- 下载停止后统计不继续增长；失败/取消后保留正确终态。
- 限额：最大时长、最大数据量、最少清理范围、超时终止自有进程。
- 诊断数据脱敏：带测试 query token 的 URL、代理认证信息、签名媒体地址不进入 JSONL、报告、UI 或 Git。
- 运行中已存在的 FluxDL 实例、用户下载目录、AppData 数据库不受测试影响。
- 设置兼容性、深浅主题、Quick Capture、下载队列与取消逻辑不回退（如果修改了这些层）。

### 真实执行验证

先读取 `package.json` 和仓库测试规范，运行受影响的实际命令，例如：

```powershell
npm run typecheck
npm run lint
npm run format:check
npm test
npm run check:rust
npm run format:rust
npm run lint:rust
npm run test:rust
npm run test:diagnostics
npm run benchmark:diagnostics
```

选择性运行真实 Windows 桌面诊断 smoke / 进程测试，**只管理本次测试启动的实例**，不停止用户正在使用的 FluxDL 或 Clash。不能把本地模拟网络测试当作真实 YouTube 吞吐测试。

### 速度提升的证据标准

- 优化前后尽量在**同一个 YouTube 测试素材、同一 format ID、同一代理配置、相同测试预算**下比较；如果条件无法对齐，不做速度提升百分比结论。
- 在可控条件下至少两次或多次采样，报告中位数和区间；真实外网样本量不足时显式说明。
- 若结果显示 0.1 MiB/s → 3 MiB/s，需有对应真实日志和相同条件证据，不能只在文档写一句“提升 30 倍”。
- 没测到明显改善时，**保留诊断与测试体系，但不默认启用实验优化**。
