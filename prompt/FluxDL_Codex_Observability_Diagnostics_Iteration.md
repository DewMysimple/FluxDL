# FluxDL — Observability & Diagnostics 工程迭代总任务书

> **用途**：将本文件作为完整任务交给在 FluxDL 工程根目录运行的 Codex，要求实际修改源码、测试、验证并提交工程交付报告。  
> **仓库**：https://github.com/DewMysimple/FluxDL  
> **方向**：运行日志工作台 + 全链路耗时追踪 + 本地 Codex 诊断报告 + 有证据的性能优化  
> **本轮原则**：**先看见问题，再定位问题，最后决定是否优化**；不得为了看起来更快而伪造指标、削弱校验或牺牲数据安全。

## 0. 你要完成的真实工作

你是一名熟悉 **Tauri 2 / Rust、React / TypeScript / Vite、Zustand、SQLite、yt-dlp 子进程和 Windows 桌面应用**的高级工程师，同时具备产品 UX、可观测性、隐私安全和性能测量经验。

FluxDL 已有 Quick Capture + Workspace 双窗口、Midnight Glass UI、yt-dlp 解析与下载、队列与持久化、下载进度和 Windows 生命周期管理。此前的工程优化已经涉及增量持久化、版本化 IPC 等；**必须以当前工作区代码为准，不能把这些历史描述当作已验证事实**。

### 本轮必须交付

1. 一个可在 Workspace 内使用的 **「诊断中心」**，有概览 / 性能分析 / 事件日志 / 异常记录，支持关联任务、筛选、搜索、定位、打开日志目录和导出诊断包。
2. Rust 主导的 **结构化日志系统**，开发版在源码根目录写可供本地 Codex 阅读的 `dev-logs/`，正式版写 Tauri 的应用日志目录；明确文件轮转、保留、错误处理、性能开销和隐私策略。
3. **端到端 Trace ID 关联和阶段计时**：前端操作、IPC、Rust 队列、yt-dlp 解析、二次安全校验、进程启动、首次有效下载进度、后处理、完成或失败均可关联。
4. `dev-logs/latest-report.md` 等 **可直接交给 Codex 的机器可读与人类可读诊断资料**。日志和报告能由实际事件自动生成，不手填、不造数据。
5. **诊断数据的统计与可视化**：按真实样本显示阶段耗时、Top 慢步骤、p50 / p95、样本数、异常原因；区分用户选择格式的停留时间与应用自身的处理耗时。
6. **证据驱动的性能改进**：先测量首次解析、二次校验、任务调度和启动耗时；只有明确发现瓶颈且能保持原有安全性时才改进代码，并提供可重复的前后对照。不必强行实现缓存。
7. 测试、文档和性能验收：结构化日志、脱敏、轮转、并发、乱序、异常退出、双窗口 UI、诊断导出与性能回归均有覆盖。

### 明确不做

- 不实现播放列表、批量下载、并发下载、全局快捷键、引擎自动更新、账号系统、云服务、远程遥测或用户行为分析 SDK。
- 不更换 React/Tauri/Rust 基础框架，不重构整个工程，不重做 Midnight Glass，不随意升级大批依赖。
- 不用模拟日志代替真实数据；UI 可用测试 fixture，但生产版不能显示虚构的性能数字。
- 不绕过 Rust 端格式合法性/来源校验，不信任客户端传来的格式与下载参数。
- 不将日志、Cookie、带鉴权参数的 URL、用户私有路径、视频标题等自动推送到 GitHub、第三方平台或外部 AI 服务。
- 不改动目前的 `release-output/FluxDL/`、`release-output/FluxDL.zip` 最新产物策略；只确保新日志不污染构建和压缩包。

## 2. 目标架构：一份可信事件，多个安全视图

推荐在 **Rust 端**建立统一诊断服务，管理日志写入、结构化事件、Trace、统计、查询与导出。React 负责采集少量前端交互时点并展示诊断数据，不直接操作任意日志文件。

建议数据流：

```text
Workspace / Quick Capture
     │
     ├─ 用户操作事件（白名单字段，operation_id）
     │
     └─ invoke + Tauri IPC
                  │
              Rust Diagnostics Service
               ├─ Trace / Span 时间关联
               ├─ 结构化事件（JSONL、持久化）
               ├─ 受控内存环形缓存 / 实时订阅
               ├─ 聚合统计与阶段耗时
               ├─ latest-report.md 生成器
               └─ 导出 ZIP（明确用户操作）
                  │
        Queue / yt-dlp Engine / Process / SQLite
                  │
       仅通过受限的 Tauri commands 提供数据给 UI
```

**不要强制照搬目录结构**；按当前代码组织落地，避免新增过多层次。可以参考：

```text
src-tauri/src/diagnostics/
  mod.rs
  event.rs               # 结构化事件 schema 与字段白名单
  trace.rs               # Trace/Span 及单调计时
  writer.rs              # 有界异步写入、轮转、容错
  redact.rs              # 录入前脱敏与敏感字段拒绝
  report.rs              # 聚合统计和最新报告
  query.rs               # 分页、筛选、按 Trace/Task 查询
  export.rs              # 脱敏诊断包

src/features/diagnostics/
  DiagnosticsPage.tsx
  components/
  hooks/
  types.ts
  diagnostics-api.ts

docs/engineering/
  observability-audit.md
  observability-design.md
  diagnostics-validation.md
  performance-analysis.md
```

如果采用 `tauri-plugin-log`，可用其普通应用日志 target、级别和轮转能力；**但它的普通文本输出本身不等于结构化 JSONL Trace 存储**。需要确认如何保证结构化事件的稳定 schema、单一真实来源和数据查询效率。可选择 `tracing` + 结构化 subscriber 或小型专用写入器，**不要同时引入三套互相重复的文件日志管线**。以当前 Rust 依赖和 Tauri 2 官方接口为准。

## 3. 结构化日志协议：真正适合 Codex 分析

### 3.1 Event Schema

需要一个带版本号、可稳定解析、各字段语义清楚的 schema。例如：

```json
{
  "schema_version": 1,
  "event_id": "evt-example",
  "session_id": "session-example",
  "trace_id": "trace-example",
  "span_id": "span-example",
  "parent_span_id": null,
  "task_id": "task-example",
  "timestamp_utc": "2026-11-09T08:00:00.000Z",
  "elapsed_since_session_start_ms": 1203.4,
  "level": "info",
  "source": "rust.engine",
  "event": "download.process_started",
  "phase": "spawn",
  "status": "ok",
  "duration_ms": 123.4,
  "fields": {
    "engine": "yt-dlp",
    "download_kind": "video"
  }
}
```

这只是 **schema 示例，不是实际运行日志**。执行时以现有模型为准，字段保持稳定，并为前端提供相应 TypeScript 类型。

最低字段要求：

- `schema_version`：便于以后迁移与兼容读取。
- `event_id`、`session_id`、`trace_id`：用于关联、去重及区分重启后的事件。
- `timestamp_utc`：用于人类查看日志发生时间。
- `elapsed_since_session_start_ms` 或等效单调时钟信息：用于**同进程**排序、对齐和阶段耗时；不要用墙上时钟差计算耗时。
- `level`：error / warn / info / debug / trace。
- `source`、`event`、`phase`：使用稳定、可筛选的事件标识。
- `task_id`：创建任务后应关联已有 Trace；尚未生成任务 ID 时允许为空。
- `status`、`duration_ms`、安全的 `fields` 与标准错误分类。

日志字段采用**白名单结构化记录**，而不是将任意对象或原始异常序列化后全量写入。尽可能将错误分为稳定 `error_code` / `error_kind`，附带安全的简述。

### 3.2 Trace / Span 关联

- 每次「解析请求」有一个 Trace；「加入队列至首次下载进度」有另一个可与解析关联的 Trace，必要时通过关联字段建立同一用户流程。
- 不要跨越用户选择格式的主观停留时间，计算所谓“软件内部等待耗时”。
- 前端可以在发起 IPC 时附上 `operation_id` / `trace_id`；后端校验其格式与长度，**绝不将其当作权限凭证**。
- Rust 内部使用 `Instant` 等单调计时工具计算本进程阶段耗时；前端可用 `performance.now()` 测量点击到 UI 反馈，但不得直接拿前端时间戳与 Rust 时间戳相减。
- 各个阶段有明确 start/end 与 success/failure/cancelled 结果，异常退出或无首个进度时应报告 **未观察到**，不能填入估计数值。
- 下载任务可能在重试时生成新的 attempt，建议用 `task_id` + `attempt_id` 区分，避免把多次尝试当成同一次耗时。
- 重复事件和 IPC 乱序不能让 Trace 状态倒退。

### 3.3 事件粒度

**默认记录高价值阶段、错误和重要操作；不要把每个下载字节、每次 React render、每次键盘输入写入文件。**

默认 Release 级别：info / warn / error；Dev 可以按模块选择 debug；更细粒度 trace 需要用户主动开启并限定时长。超高频进度只用于 UI，必要时每隔一定时间采样/聚合到诊断系统。

## 4. 最重要的功能：解析到下载的全链路耗时

请仔细对照真实代码路径埋点，而不是只在外层包一个 `Instant` 就宣称覆盖全链路。

### 4.1 阶段清单

| ID | 阶段 | 典型起止点 | 注意事项 |
|---|---|---|---|
| P01 | `parse.ui_request` | 前端点击解析 → 收到后端响应 | 前端独立测量 UI 感知耗时 |
| P02 | `parse.ipc_dispatch` | Rust command 收到请求 → 开始验证/执行 | 不直接与前端不同步时钟相减 |
| P03 | `parse.validate` | URL、引擎配置与参数检查 | 不记录原始 URL / Cookie |
| P04 | `parse.engine_spawn` | 准备启动 → yt-dlp 子进程创建完成 | Windows 进程启动耗时 |
| P05 | `parse.metadata_extract` | 子进程启动 → 元数据实际准备完成 | 可进一步区分进程读取与 JSON 解析 |
| P06 | `parse.response` | Rust 结果封装 → IPC 返回 | 不把网络等待归因于 IPC |
| P07 | `enqueue.validate` | Rust 收到加入队列 → 基本合法性检查完成 | 区分本地校验与网络访问 |
| P08 | `enqueue.metadata_recheck` | 如果当前实现存在二次解析，测实际持续时间 | **高优先观测项**，不先删除 |
| P09 | `enqueue.persist` | 任务创建 → 关键状态写入完成 | 区分 DB 排队和真正写入 |
| P10 | `queue.wait` | 入队 → 开始调度 | 串行任务自然等待要单独显示 |
| P11 | `download.engine_spawn` | 开始进程启动 → 进程创建完成 | 区分 yt-dlp 初始化与本地 spawn |
| P12 | `download.first_progress` | 进程创建完成 → 首个**有效**进度事件 | 不要误写成“首字节下载时间” |
| P13 | `download.active` | 首个有效进度 → 下载阶段结束 | 供诊断，别按每帧写文件 |
| P14 | `download.postprocess` | FFmpeg 合并或转码阶段 | 若未发生应显示“不适用” |
| P15 | `download.terminal` | 完成 / 失败 / 取消 → 最终状态持久化 | 保证终态、进程退出和 DB 对齐 |

请根据真实项目合并或调整阶段，但至少覆盖：**首次解析、二次校验（如存在）、排队、进程启动、首次有效进度、后处理、最终状态**。

### 4.2 三种必须分开的指标

- **解析等待**：用户主动发起解析后，直到预览可用的时间。
- **加入队列到开始下载**：用户点击加入队列，直到任务进入有效下载阶段；进一步分解安全校验、DB、排队、spawn、等待首次进度。
- **完整下载用时**：真正下载与后处理各自耗时，不包含用户在 UI 上挑选格式的思考时间。

若某次下载没有 yt-dlp 进度输出，正确状态为“进程已启动 / 尚未收到有效进度”，不能写成“正在连接媒体源”除非底层确实提供此阶段的信号。

### 4.3 用户可见的状态反馈

利用已经确认存在的后端事件，将“准备中”细分为**真实可证实的状态**：

- 校验参数中。
- 复核媒体信息中（仅当确实执行）。
- 等待队列。
- 启动下载引擎中。
- 进程运行，等待首次进度。
- 下载中。
- 后处理中（确实存在时）。
- 完成 / 失败 / 已取消。

不要通过前端定时器伪造状态转换，不要改变现有下载队列语义。

## 5. 日志目录、文件命名和 Codex 可读性

### 5.1 开发版

在 **FluxDL 源码根目录**创建以下结构（只用于 debug / 开发构建）：

```text
FluxDL/
  dev-logs/
    latest-report.md
    sessions/
      session-<timestamp>-<id>.jsonl
    errors/
      errors-<timestamp>-<id>.jsonl
    .internal/             # 可选：内部轮转状态；若无需则不建
```

路径要从可靠的开发根目录配置/发现，不应依赖当前工作目录恰巧正确；允许开发配置明确指定路径。**发布版必须禁止回退写入源码路径。**

- `sessions/*.jsonl`：真实结构化事件，单行独立 JSON，对未完整写入的尾行可安全跳过并报告。
- `errors/*.jsonl`：可选的异常索引，可从主事件索引生成；避免造成不必要的重复存储和不一致。
- `latest-report.md`：最近一次或最近一个有效时间窗口的自动诊断报告，明确数据区间、运行模式、样本数量、trace id 与性能摘要。程序运行中应可主动刷新，正常退出和应用启动后也可更新，不能只在关闭时才存在。
- 开发版实际启动后应能直接从资源管理器打开本目录；本机 Codex 可直接读取这些文件并与源码对照。

`.gitignore` 必须忽略 `dev-logs/` 及生成的所有诊断包。**不可通过加 `!` 规则误把真实日志上传公开仓库。** 如需要测试 fixture，应放到独立 `tests/fixtures`，内容为无敏感数据的人工合成样例。

### 5.2 正式版

- 写入 **Tauri 2 应用日志目录**，Windows 通常位于 `%LOCALAPPDATA%/<bundle-identifier>/logs/`；具体由当前 Tauri 配置/路径 API 获取，**不要硬编码用户目录**。
- 正式版仍可在软件内查看日志、打开所在目录并导出诊断包。
- 不写入 exe 旁边、安装目录、源码目录或 `release-output/`。
- 不因软件升级、重新打包或替换 `release-output` 而自动删除用户诊断历史。

参考 Tauri 2 官方日志文档：
https://v2.tauri.app/plugin/logging/

### 5.3 文件保留和轮转

给出合理默认值，可以随代码实现微调：

- 单文件推荐最大约 **10 MiB**。
- 单类最多保留 **5 个轮转文件**。
- 一般会话日志保留约 **7 天**。
- 单次会话摘要保留合理数量；`latest-report.md` 始终反映最近可分析的数据。
- 过期或超额文件在安全边界内清理；不清除用户主动导出的报告。
- 清理仅针对由 FluxDL 创建的已知日志文件，不允许对上级目录做递归危险删除。
- 日志写入失败应降级运行并产生一次性可见的诊断提醒，**绝不能因为磁盘满、路径无权限、文件被占用而导致视频下载崩溃**。

### 5.4 性能要求

- 文件写入不要持有任务状态锁或阻塞读取 yt-dlp stdout/stderr 的热路径。
- 推荐有界队列 / 独立 writer；高频调试事件超限时可合并/丢弃并计数，关键错误尽最大努力保存。
- 避免多窗口各自争抢同一个文件句柄，由 Rust 单点控制文件日志。
- 可维护受限大小的内存缓存（例如近 2,000 事件）供 UI 实时显示；大量历史通过分页查询磁盘，不一次性塞给前端。
- 对轮转、Windows 文件锁、进程异常结束后的破损尾行进行容错。

## 6. 隐私与安全：日志默认必须安全

**日志属于敏感本地数据，安全优先级高于排错方便。**

不得在普通日志、JSONL、`latest-report.md`、UI 或导出包中泄漏：

- 完整媒体 URL、query 参数、token、签名参数、下载站点带认证信息的地址。
- Cookies、浏览器 Cookie 文件内容、鉴权 Header、代理凭据。
- 原始 yt-dlp 命令行中的潜在敏感参数。
- 剪贴板内容、完整视频标题、个人文件名和本地绝对路径（默认）。
- 用户账户名、家庭目录、系统环境变量值、与诊断无关的个人数据。

### 6.1 采用白名单而不只是正则替换

- 优先记录 `phase`、`duration_ms`、`error_code`、`task_id`、格式类型、引擎版本、成功/失败等安全元数据。
- 若需要来源信息，优先使用可控的来源类别（例如 `youtube` / `other`），不需要完整 URL；如果记录 hostname，先明确隐私风险并提供关闭选项。
- 对引擎原始 stderr 的记录尤其谨慎：它可能含 URL、文件名或 Header，不得未处理直接落盘或展示。
- 对异常信息采用“错误类别 + 安全摘要 + 可选经过脱敏的短文本”，并限制长度。
- 导出与 UI 使用已净化的数据，**不要只在导出阶段脱敏，而让原始敏感数据留在磁盘**。
- 对未知字段默认拒绝存储，不能把任意 JavaScript 对象直接 `JSON.stringify` 写日志。
- 避免开放前端任意文件系统权限；通过参数受限的 Rust 命令查询日志、打开**应用可信日志目录**或导出用户明确选择的位置。

### 6.2 受控导出

- 诊断 ZIP 必须由用户明确触发，且导出前能看到要包含的文件和隐私提示。
- 不添加自动上传、Sentry、远程日志、AI API、后台同步、崩溃数据上报。
- 在文档中明确指出“本地 Codex 可以读取同机器工程目录日志；仅看 GitHub 的远程 Codex 不会自动获得本机 dev-logs”。

### 6.3 安全测试

准备带有假 Cookie、测试 token、带 `?sig=...` 的 URL、Windows 用户路径、代理密码等**虚构敏感数据**，证明在 JSONL、UI 查询结果、Markdown 报告和 ZIP 内均不存在明文泄漏。不要在测试里放任何真实凭据。

## 7. Workspace「诊断中心」UI（Midnight Glass）

这是**真正可用的页面**，不是静态展示或 Mock Dashboard。继续沿用当前 UI Token、字体、圆角、侧栏、图标、暗浅主题，不新增独立设计风格。

### 7.1 导航与页面结构

- 在 Workspace 左侧导航底部增加 `诊断中心`，图标可以选 Activity / Scan / Terminal 一类，与其他导航一致。
- Quick Capture 不增加完整诊断页面，但支持从当前任务的操作入口定位到 Workspace 对应 Trace（如果现有信息结构允许）。
- 诊断中心至少包含四个视图：**概览、性能、事件、异常**。可以是 Tab，也可采用现有导航模式。
- 页面有当前日志状态：记录正常 / 日志写入受限 / 无数据，并在必要时展示日志目录位置和记录级别。

### 7.2 概览

显示真实数据：

- 本次会话的解析次数、下载任务次数、错误数。
- 最近若干样本的“解析到预览”耗时、“加入队列到首次进度”耗时；无样本时显示 `暂无数据`。
- 慢步骤 Top N（含样本数量、p50 / p95、最慢实例 Trace）。
- 最近错误事件（可点击打开详情）。
- 快捷操作：`查看事件`、`打开日志目录`、`导出诊断包`、`复制 Trace ID`。

**不显示未经真实采集的“6.8s”“100% 成功”等演示值。**

### 7.3 性能分析

- 按单个 Trace 展示阶段时间轴/瀑布图，并列出耗时和状态。
- 分清楚**执行阶段**与**排队等待阶段**，并标识用户操作停顿不计入内部耗时。
- 高亮最长阶段，允许展开查看阶段详情、开始/结束时间、错误分类。
- 提供时间范围、任务/Trace 筛选、慢 Trace 排序、p50/p95 与样本数。
- 若阶段缺失或进度从未到达，显示 `未观测到` 或 `超时/中断`，不补造值。
- 可选提供两次真实采样的对比；避免为 MVP 引入复杂的多版本分析数据库。

### 7.4 事件日志

- 时间、级别、来源、事件名、阶段、Trace、任务、耗时与安全上下文。
- 搜索和筛选：关键字、时间范围、级别、来源、任务 ID、Trace ID。
- 日志内容适量虚拟列表/分页，不能因几万条记录冻结窗口。
- 允许复制单条事件、复制 Trace ID、定位相关任务或性能视图。
- 新事件实时更新，但**不要因为 UI 没打开而停止文件记录**。
- 若页面停在较早记录，实时追加不能粗暴抢走滚动位置。

### 7.5 异常记录

- 按 Trace / Task 关联错误链路。
- 展示错误发生阶段、分类、脱敏安全摘要、实际耗时和可采取的排查动作。
- 可从错误条目直接打开对应完整 Trace。
- 任何任务失败都必须有可追踪的错误记录；无需把业务错误重复写几百次。

### 7.6 视觉和微交互要求

- 坚持深石墨 + 银紫的 Midnight Glass；主页面以哑光为主，浮层柔和磨砂。
- 使用真实图表数据、适度留白和细腻状态反馈。
- 正文、数据、表头的对比度和可读性优先，不滥用发光、渐变或无意义动效。
- 性能瀑布图可只用 SVG/CSS 轻量实现；如现有栈足够，不额外安装重型图表库。
- 深浅主题、缩放、高 DPI、键盘焦点、减少动画偏好可用。
- 使用空状态、错误状态和载入状态的完整设计。

## 9. 自动生成 Codex 诊断摘要和导出包

### 9.1 开发目录中的 latest-report.md

报告应自动生成真实信息，结构建议：

```markdown
# FluxDL 最新运行诊断

- 生成时间：...
- 采样会话：session-id
- 代码版本：Git commit（若可安全获取）
- 应用版本 / 运行模式：...
- 事件范围：起始 UTC 至结束 UTC
- 样本数量：...

## 关键耗时
| 阶段 | 样本数 | p50 | p95 | 最慢 | 关联 Trace |
| ... | ... | ... | ... | ... | ... |

## 慢操作 Top N
...

## 异常汇总
...

## 可以继续排查的代码路径
- （使用已知 source/module 标识，仅当代码实际存在）

## 数据局限与说明
- 缺失事件、外部站点影响、样本过少、未观测指标等

## Codex 建议读取的本地文件
- dev-logs/sessions/...jsonl
- dev-logs/errors/...jsonl
```

- 没有足够数据时写“样本不足”，不得把 1 次采样说成可代表整体的 p95。
- 结果必须可从原始 JSONL 复算；提供生成命令或程序内动作。
- 记录源代码模块/阶段标识，帮助 Codex 检索相应函数，但不臆测具体原因。
- **不要**让日志自动调用 Codex 或任何 AI 服务；只提供 Codex 可直接阅读的本地资料。
- 需要控制报告长度和时间范围，避免数千页不可读报告。

### 9.2 导出诊断 ZIP

用户明确点击导出时，生成安全、脱敏、可检查的 ZIP，例如：

```text
FluxDL-Diagnostics-<timestamp>.zip
  summary.md
  events.jsonl
  errors.jsonl
  environment.json
  privacy-manifest.json
  README.md
```

- `environment.json` 仅含必要的应用版本、OS 大版本、架构、yt-dlp/FFmpeg 版本、脱敏后配置概要；不能包含绝对路径、真实密钥或完整环境变量。
- `privacy-manifest.json` 指出数据包含哪些类别、已排除哪些敏感类别以及生成时的脱敏策略。
- 不收集 SQLite 数据库本体，不打包完整用户下载目录，不打包原始 yt-dlp 命令行或完整 stderr。
- 如果有不确定是否敏感的字段，默认省略。
- ZIP 文件名和路径由用户确认；禁止自动上传。
- 导出后可以通过系统资源管理器定位文件，不误导用户“已经分享给 Codex”。

### 9.3 给 Codex 的后续排错使用方式

在 README 或 `docs/diagnostics.md` 中写清楚：

> 在本地 Codex 中打开 FluxDL 工程，先读取 `dev-logs/latest-report.md`，再按报告里的 Trace ID 查询 `dev-logs/sessions/*.jsonl`，核对阶段耗时和相关 Rust/React 代码路径；优化前后使用相同测试条件复测。不要直接把本地日志提交 GitHub。

## 10. 基于证据的真实性能优化

**必须先有日志与性能基线，再修改下载链路。** 这是重要验收原则。

### 10.1 建立可重复测试

至少准备两类场景：

**A. 确定性本地测试（用于工程性能回归）**

- 利用已有假引擎 / fixture 或本地媒体 HTTP 服务。
- 可控制解析延迟、校验延迟、spawn 延迟、首个进度延迟和失败条件。
- 不依赖 YouTube 或任何互联网网站的稳定性。
- 每个场景重复多次，输出 p50、p95、样本量、运行环境。

**B. 真实 yt-dlp 手动联调（用于实际感知）**

- 使用合法可下载、稳定的公开视频或用户许可测试素材。
- 记录 yt-dlp 版本、格式、是否启用代理、缓存状态、网络环境（非敏感摘要）。
- 外部站点和网络变化大，不把一次真实下载耗时当成工程回归结论。

至少覆盖：解析成功、解析失败、加入队列、二次校验、串行排队、spawn 失败、没有首个进度、取消、下载失败、后处理以及成功完成。

### 10.2 报告真实瓶颈

生成 `docs/engineering/performance-analysis.md`：

- 每个关键阶段的样本数、p50 / p95 / 最大值。
- 已确认的最长阶段及代码路径。
- 它属于应用自身耗时、yt-dlp 子进程耗时、外部网络耗时，还是排队等待。
- 可信度和无法确定的部分。
- 最值得尝试的优化方案以及预计风险。

### 10.3 只在证据充分时优化

如果测量表明 **加入队列后的二次解析**显著影响体验，可以研究短期可信元数据复用：

- 必须由 Rust 保存后端先前验证过的元数据，前端只能持有短时引用/令牌。
- 令牌要有过期时间、绑定必要上下文、严格校验格式与下载模式。
- 不能绕过后端的下载参数、目标路径和引擎检查。
- 站点媒体 URL 过期、格式不可用、权限变化等场景必须自动失效并安全回退到重新解析。
- 缓存不能把认证材料、原始 URL 或 Cookie 写进持久化日志或导出包。
- 要求有缓存命中、未命中、过期、回退及并发边界测试。

**如果实测瓶颈不在二次解析，就不要强行引入缓存。** 可以根据实际证据改进其它阶段，例如减少不必要的串行校验、消除重复 IPC、避免队列中不必要的同步 I/O。

任何性能优化必须保留相同校验与下载正确性；如果重构前后无法得到可靠结果，标注未完成，不得宣称“速度提升 X 倍”。

## 11. 健壮性与异常测试

### 11.1 日志写入与恢复

测试：

- 多线程 / 异步并发写入，不产生交错 JSON 行。
- 文件达到轮转上限、超过保留天数后正确清理。
- 文件被占用、目录只读、磁盘不足、路径不存在。
- 文件尾行因异常退出而截断，读者可忽略并给出提示。
- 非法 JSONL 行、未来 schema 版本、重复 event_id。
- 写入队列满：只丢弃允许丢弃的低优先级事件，有明确 dropped count 指示；不能拖慢下载热路径。
- 进程异常结束后重新启动，新 session 能正确区分与继续写入。

### 11.2 Trace 正确性

测试：

- 同一用户操作跨前后端可找到对应 Trace。
- 前端与 Rust 墙上时钟存在偏移时，计算出的后端阶段耗时仍正确。
- 取消与完成竞态不产生两个互相矛盾的终态。
- 二次解析失败、首次进度缺失不会让总时长假装正常完成。
- 快速重复解析不会把不同 request 的事件合并。
- 同一任务重试生成独立 attempt，且仍能关联原 task。
- 双窗口打开、关闭、重新打开后仍可查询完整诊断历史。

### 11.3 隐私回归

对 Rust 结构化写入器、前端展示、report、ZIP 进行**端到端脱敏测试**。虚构敏感字符串一旦出现于任意用户可见或输出文件，测试应失败。

### 11.4 UI 回归

- Midnight Glass 深浅主题正常。
- Workspace 导航、任务队列、Quick Capture 正常。
- 日志页大量记录时支持翻页 / 虚拟列表，不发生明显冻结。
- 复制 Trace、打开日志目录、导出 ZIP 的操作确实有结果。
- 空日志、日志不可写、记录损坏等有用户可理解的状态提示。
- 不为排错增加对用户无关的弹窗或频繁 Toast。

## 12. 实施顺序：按可独立验收的阶段推进

请按顺序执行，阶段完成后再进入下一阶段，不要一次性重写全部模块：

| 阶段 | 目标 | 完成判据 |
|---|---|---|
| 0 | 现状审计 | 理清真实调用链，生成审计文档 |
| 1 | 结构化日志与安全写入 | dev/prod 路径、Schema、轮转、脱敏、容错均验证 |
| 2 | Trace + 阶段计时 | 从解析到下载首次进度的关键链路完整可追踪 |
| 3 | Codex 诊断报告与 ZIP 导出 | 自动生成 `latest-report.md`、JSONL 和受控导出 |
| 4 | 诊断中心 UI | 概览、性能、事件、异常实际可用 |
| 5 | 测量与性能分析 | 有真实可复算的阶段统计与可重复基线 |
| 6 | 针对性优化 | 仅在已证实有收益时修改瓶颈；有前后对比 |
| 7 | 全量回归与文档 | 测试、构建、日志安全、双窗口、产物策略不回退 |

每个阶段要求：

1. 说明将变更哪些模块。
2. 先补充必要测试或 fixture。
3. 实现真实功能。
4. 执行对应验证并修复回归。
5. 更新文档，确认没有敏感数据或无关文件。
6. 进入下一阶段。

如果上下文或环境不足以完成全部阶段，应优先完成阶段 1–4 的可用系统，并把剩余工作列出准确阻碍，不留下无法编译的半成品。不要为了宣称完成而伪造结果。

## 15. 验收标准（必须逐项说明）

- 在软件内进入诊断中心。

- 如何让本地 Codex 阅读 `dev-logs/latest-report.md`。
- 如何生成、查看、导出安全诊断包。

- 日志轮转、保留、隐私与不上传原则。

最终请用以下结构回复：

1. **实际完成内容**：按阶段列出实现结果和关键文件。
2. **目录和 UI 入口**：真实开发路径、正式日志路径、Workspace 导航、导出位置。
3. **Trace / Schema**：给出实际数据类型及真实或明确标注 fixture 的示例。
