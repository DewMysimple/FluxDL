# 版本化增量事件与快照恢复

选择者：Agent在用户授权的0.2工程优化范围内实施；用户要求Rust唯一运行时权威、双窗口可靠同步、减少全量广播并处理初始化/丢失竞态，未指定内部协议形式。

采用`app-state-changed`的`{sessionId,revision,change}`。关键ack后同锁捕获单任务/设置等语义事件，普通runtime/log按250ms合并，不构造完整snapshot再diff。publisher锁外按revision发送。数据库版本、运行attempt与IPC revision独立，避免把内部合并误作前端缺口。

保留完整snapshot恢复，前端先监听再请求，有限缓冲并按连续revision应用；旧请求不得回退可信cache，未知session仅触发权威快照。更高revision详情也只能触发恢复，不能跳过全局事件。恢复水位覆盖请求期间新观察到的缺口/错误/详情，失败可重试且卸载清理。

加入6秒正常有序checkpoint：健康状态仅推进版本，没有领域重渲染；唯一终态丢失后即使没有后续业务事件也能暴露缺口。代价是低频小包和恢复snapshot的全量成本，换取末帧可恢复，而非仅依靠用户聚焦。

snapshot/详情最终短锁先flush全部pending日志与progress，再克隆状态和revision，防重复append；FullUpsert清pending。日志保留真实重复文本，限制100行/1600字符，不用文本去重或第二套log cursor。特殊旧任务ID使用null原型字典；终态普通progress被拒绝，合法新流reset通过完整单任务事件表示。

实现状态：阶段4已通过Rust58项及独立fixture/fmt/严格Clippy、前端64项/type/lint/format和真实双窗11项回归。实际同流程每窗事件字节377855→50858；79条正常退出前与4条异常退出前两窗观测序列相同。具体测量范围、吞吐限制和最终阶段5/6复测见工程验证报告，不能把阶段4数据冒充最终构建结果。
