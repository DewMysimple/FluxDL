# 队列与持久化实现边界

SQLite 使用系统 AppData 中的 `fluxdl.sqlite3`，采用单连接、事务和 `synchronous=FULL`。设置与任务状态变化立即保存；下载进度至多约每两秒保存一次。应用重启时，所有残留活动任务（包括等待中的任务）标记为“已中断”，需要用户主动重试。数据库内容损坏时先将原文件保存在带时间戳的备份中，再建立新数据库，并在诊断中提示。

当前 MVP 在 Rust 后端异步运行时的线程内执行短同步 SQLite 事务，保存操作持有队列状态锁。它不会直接阻塞窗口主线程，但数据库读写期间，其他需要该锁的 IPC 请求、队列操作和进度通知会等待。当前保存会序列化并写入全部任务，而不是仅更新变化的记录。

这是面向个人本地使用的实现取舍。大量历史记录或每项任务都带有大量诊断日志时，事务可能明显延迟；本版本没有完成大规模历史记录的性能基准，也没有声明记录数量或延迟保证。日志已限制为每任务 100 行、每行 1600 字符，管道读取单行缓冲最多 8192 字节，进度通知约每秒四次。文件存在性检查使用异步文件 API，不持有队列状态锁。

后续若要支持大量记录，应将 SQLite 移到独立阻塞工作线程或数据库 actor，按任务增量写入并为历史查询分页；不应单纯提高同步保存频率。应用不会为了控制历史数量而自动删除记录或本地媒体文件。

Windows 的下载、版本检查和媒体解析进程会在启动后立即加入设置了 `KILL_ON_JOB_CLOSE` 的 Job Object。取消、应用退出或异常结束会清理已加入该组的后代进程。存活进程若无法加入进程组，应用保守停止；极快退出的命令会先通过系统进程句柄确认其已结束，再继续校验退出码。当前没有实现挂起创建，因此启动与加入组之间仍有极短的时间窗口。非 Windows 平台当前仅保证父进程的取消，尚未验证完整子进程组语义。
