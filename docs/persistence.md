# 队列与持久化实现边界

SQLite 使用系统 AppData 中的 `fluxdl.sqlite3`，采用单连接、事务和 `synchronous=FULL`。0.2 工程优化已将数据库连接交给独立标准线程，由有界队列接收单任务增量变更，COMMIT 后回执；主任务状态锁内不执行数据库 I/O。日志仍限制为每任务 100 行、每行 1600 字符，管道单行缓冲最多 8192 字节。

新任务、重试、删除记录、设置和终态采用候选 → 锁外写入确认 → 内存/事件发布。完成状态在数据库确认前也不会出现在完整快照中；真实进程已经结束但最终保存失败时，保留待确认结果与可读诊断并重试。公开命令的等待者退出不会取消已接受的后端提交操作。回执丢失会按版本及文档只读核对，未确定时不能假装回滚或成功。

进度由独立异步执行器约每两秒保存最新脏任务，避免 stdout/stderr 读取等待磁盘；取消先接受意图并向真实进程发信号，再确认取消状态。单调存储序号、执行 attempt 和持久 tombstone 阻止旧更新及删除后复活；存储序号与后续 IPC 事件版本各自负责不同边界。

Schema v2 保留旧设置与任务文档表，仅增版本表；v1/v0 可识别结构在事务内迁移，未来或不兼容结构拒绝修改。未知任务状态、坏 JSON、ID 不一致的行原文保留并显示诊断，其余可理解记录继续加载；更新已知记录时保留嵌套未知 JSON 属性。保留行当前不可操作，不把未知状态猜成已完成。只有 quick_check 确认物理损坏才使用原有字节备份恢复，语义解码错误不会触发空库重建。

应用重启仍将所有可理解的活动任务（包括 queued）标为 Interrupted，不自动下载。关闭用一个总 deadline 覆盖取消、终态确认和 flush；正常写入失败/超时会恢复任务接纳及唯一执行器，未决请求在后台收敛后继续使用。存储结果永久无法核实时，相关关键候选会保留并阻止后续关键提交，界面仍可读取诊断；不能承诺损坏或不可访问磁盘时仍能可靠创建新任务。

常规进度快照使用文件可用性缓存。显式完整快照（包括 focus 重新同步）强制刷新文件信息，详情仅检查该任务；刷新 token、任务版本及最终路径共同拒绝过期检查结果。打开文件仍真实校验路径与存在性，缓存不用于授权。文件系统 I/O 不持有任务状态锁，但显式刷新大量历史仍有成本。

100 / 1,000 / 5,000 条历史的真实生产路径性能数据见 [重构前基线](engineering/0.2.0-performance-baseline.md)与[阶段 3 复测](engineering/0.2.0-performance-after.md)。这不构成记录数量或延迟保证。阶段 4 已接入带 session/revision 的增量事件、按需详情和六秒 checkpoint；完整恢复快照仍保留，其日志在同锁原子 flush 后克隆，协议见 [IPC 合同](engineering/ipc-plan.md)。整体事件流量和最终性能由后续集成回归实测。应用不会自动删除历史或媒体。

Windows 的下载、版本检查和媒体解析进程会在启动后立即加入设置了 `KILL_ON_JOB_CLOSE` 的 Job Object。取消、应用退出或异常结束会清理已加入该组的后代进程。存活进程若无法加入进程组，应用保守停止；极快退出的命令会先通过系统进程句柄确认其已结束，再继续校验退出码。当前没有实现挂起创建，因此启动与加入组之间仍有极短的时间窗口。非 Windows 平台当前仅保证父进程的取消，尚未验证完整子进程组语义。
