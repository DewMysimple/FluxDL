# 0.2.0 最终性能复测

最终原始数据：[Rust](performance-final.json)、[前端](frontend-final.json)。重构前数据仍为[performance-before.json](performance-before.json)、[frontend-baseline.json](frontend-baseline.json)，没有覆盖。阶段2/3/4中间数据另外保留，不作为最终值。环境、确定性配方、nearest-rank分位数和测量边界见[基线](0.2.0-performance-baseline.md)。

## 复现

在同一Windows x64环境、无其他构建/压力任务时实际执行：

```powershell
npm run benchmark:rust -- --output docs/engineering/performance-final.json --label after-final --samples 20 --progress-writes 20
npm run benchmark:frontend -- --phase after-final --output docs/engineering/frontend-final.json
```

Rust使用20样本，每批20次progress保存，DELETE journal/FULL synchronous；新增/更新/终态通过生产PersistenceWriter、有界通道、SQLite owner线程及durable ack计时。删除复位和终态复位不计入对应操作。临时DB自动清理，不访问用户数据库/媒体网络；额外Manager初始化只做本地工具版本检测。前端沿用20次store/5次React样本、一次warm-up，JSON解码不计入状态更新时间。

## 数据库：before → final

单位ms，每格为p50 / p95。数据库加载的前后工作范围不同，见下节。

| 历史数 | 数据库加载 | 新增 | 单条更新 |
| --- | ---: | ---: | ---: |
| 100 | 10.115 / 11.076 → 2.648 / 2.861 | 3.391 / 4.179 → 2.714 / 2.943 | 3.382 / 4.211 → 2.084 / 2.690 |
| 1,000 | 50.808 / 58.948 → 10.564 / 10.854 | 11.634 / 27.496 → 2.134 / 2.642 | 21.432 / 38.619 → 2.117 / 2.405 |
| 5,000 | 506.773 / 600.938 → 50.624 / 51.397 | 98.855 / 109.913 → 2.183 / 2.711 | 98.835 / 109.543 → 2.095 / 2.339 |

| 历史数 | 20次progress保存总耗时 | 终态保存 |
| --- | ---: | ---: |
| 100 | 63.554 / 73.218 → 44.581 / 50.037 | 3.092 / 4.803 → 2.068 / 2.455 |
| 1,000 | 293.757 / 390.580 → 43.641 / 45.780 | 10.588 / 22.688 → 2.104 / 2.258 |
| 5,000 | 2016.538 / 2211.423 → 42.394 / 44.351 | 76.451 / 151.460 → 2.074 / 2.239 |

单条写入不再随全历史集合重写，5000条单更新p50约为before的1/47。小集合仍有durable commit/线程调度固定成本，不把该比率推广为端到端下载速度或所有机器的保证。

**加载不是应用启动。** before open包含全部文件stat和启动全表保存；final open/load/close不做文件检查，增加旧日志/错误/warnings的内存脱敏。显式文件刷新被移到snapshot/详情，因此506.773→50.624ms不能称为端到端启动同比加速。

阶段3加载5000条p50为38.482ms，最终为50.624ms；增加旧诊断安全过滤带来线性读取成本，另有采样/调度噪声。这里保留安全过滤，没有为了较小数字让旧凭据重新进入UI。阶段3原始数据在[performance-after.json](performance-after.json)。

## 完整快照及成本迁移

| 历史数 | JSON序列化before → final（p50 / p95 ms） | payload before → final（B） |
| --- | ---: | ---: |
| 100 | 0.139 / 0.175 → 0.105 / 0.146 | 108584 → 108629 |
| 1,000 | 1.233 / 1.560 → 1.304 / 1.341 | 1081484 → 1081529 |
| 5,000 | 13.365 / 20.619 → 6.819 / 7.069 | 5413484 → 5413529 |

完整snapshot增加45B版本元信息，没有缩小；收益来自减少高频使用。未更换序列化算法，1000条p50轻微变慢、5000条变快仍包含缓存/系统负载差异，不能归因于IPC优化本身。

真实Manager显式snapshot（状态克隆+文件检查+令牌校验）最终101/1001/5001条p50/p95分别为2.770/2.930、27.235/27.753、154.264/156.903ms；无独立before值。普通progress不执行这批stat，详情只刷新请求项；完整恢复仍是随历史量增长的成本。

## 前端最终结果

这是React开发构建+jsdom中的实际store/controller/reducer，非WebView传输或FPS。受影响任务为一个active，History显示其余已完成任务；最小元数据/空日志是可比较下界。每组20次更新均20次通知，无关历史行render和History React commit均为0。

| 任务数 | 负载 | payload B | store p50 / p95 ms | 更新至effects p50 / p95 ms |
| --- | --- | ---: | ---: | ---: |
| 100 | 完整snapshot | 67381 | 0.282 / 0.339 | 0.331 / 1.244 |
| 1,000 | 完整snapshot | 670381 | 2.780 / 4.515 | 3.666 / 7.117 |
| 5,000 | 完整snapshot | 3362381 | 14.572 / 16.321 | 18.380 / 21.132 |
| 100 | taskProgress增量 | 252 | 0.023 / 0.070 | 0.031 / 0.072 |
| 1,000 | taskProgress增量 | 252 | 0.151 / 0.193 | 0.465 / 0.781 |
| 5,000 | taskProgress增量 | 252 | 0.877 / 0.930 | 3.900 / 4.323 |

before的5000条每次重渲染4999个无关历史行，更新至effects p50为2509.177ms；最终完整snapshot为18.380ms，增量为3.900ms。该夹具没有显示active任务行，0 commit不表示产品中的相关下载行也不更新。

before纯setter p50约0.011ms，因为只是替换数组，昂贵React工作发生在计时外；最终setter需要结构比较或字典复制，5000条完整snapshot为14.572ms、增量为0.877ms。该局部指标变慢必须与render/effects一起理解，不能只挑单一最快数字。不可变字典复制仍O(N)，未声称常数时间。

## 真实IPC：保持受控流程可比

[ipc-before.json](ipc-before.json)与[ipc-stage4.json](ipc-stage4.json)来自相同11项真实桌面流程、每个窗口单独记录UTF-8 payload，排除传输framing；任务较少，不拿它冒充5000历史。阶段4控制组源码已包含版本增量协议，阶段5/6未改变wire；最终扩大回归的事件量另列，不把不同工作负载的总量直接同比。

| 每窗口指标 | before全量广播 | 阶段4相同流程 |
| --- | ---: | ---: |
| 事件总数 | 69 | 83 |
| 总payload B | 377855 | 50858 |
| 常规数据包p50 / p95 B | snapshot 6366 / 6550 | progress 347 / 590 |
| 观察峰值/秒 | 所有snapshot 5 | 仅progress 3 |
| 旧app-state-updated | 有 | 无 |

总字节减少86.5%，事件数因语义包与checkpoint增加。后端配置250ms普通progress合并，语义变化不受该节流；不同类型峰值不能混作同一频率指标。两窗79条正常退出前+4条异常退出前观测的session/revision/type/taskId/bytes按序一致。前端合成252B不等于真实进度347B。

最终扩大15项回归（seed/MP3/错误协商）另见[ipc-final.json](ipc-final.json)：每窗90事件、56130B，44个progress中位347B/p95 590B、观察峰值4/秒，无旧全量广播；86+4条双窗观测序列相同。因为工作负载扩大，其总量不与before控制组直接同比。后续修复的引擎内部formatter与页脚版本不参与DB/History基准的操作代码，原始final采样保留。

## 限制

未测端到端应用启动、IPC延迟、GPU绘制/FPS或峰值内存。5个React样本的p95即最大观测值；缓存、磁盘和Windows后台调度会影响小量级耗时。完整恢复和大型元数据仍有成本，不能将本次单机结果写成普遍性能保证。进程故障、数据兼容和实际构建/回归范围见[验证报告](0.2.0-validation-report.md)。
